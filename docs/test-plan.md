# Тест-план: розрахунок вартості поїздки, тарифи версії 3

Майстер тест-план за розділами ISO/IEC/IEEE 29119-3. Основа — `docs/spec/tariffs.md`, версія 3,
затверджена й чинна з 2026-09-15 (`:5`–`:8`). Рядки `:N` без файлу — у `docs/spec/tariffs.md`.
Чого специфікація не визначає — у «Відкритих питаннях», а не в очікуваннях.

## 1. Контекст тестування

### 1.1 Проєкт / рівень тестування

Реліз — розрахунок вартості поїздки за тарифами v3, що замінюють v2 (`:11`): додано нічну знижку
T10, ліміт 250 → 300 грн, збір T7 100 → 150 грн (`:151`–`:155`). Майстер-план для всіх рівнів:
статичного, модульного, інтеграційного (API), системного. Оракул — специфікація: якщо програма чи
чек розходяться з нею, правильна специфікація (`:15`–`:18`); кожен тест і дефект посилається на
ID правила T1–T10 (`:18`–`:19`).

### 1.2 Об'єкти тестування

| Об'єкт | Шлях | Правила |
|---|---|---|
| Розрахунок поїздки `quote(ride, rider, options)` | `app/src/tariff.js` | T1–T5, T7–T10, розд. 4 (`:43`–`:149`) |
| Денний ліміт (журнал нарахувань за київську добу) | `app/src/day-cap.js` | T6 (`:100`–`:103`) |
| Станції й зони | `app/src/zones.js` | додаток А (`:164`–`:176`) |
| Київський час | `app/src/kyiv-time.js` | `:37`, доба (`:34`) |
| Чек | `app/src/receipt.js` | T9 (`:129`–`:135`) |
| HTTP API `POST /api/quote`, `GET /api/health` | `app/src/server.js` | розд. 4 (`:147`–`:149`) |
| Сторінка | `app/public/index.html` | — (лише smoke) |

### 1.3 Межі тестування

**У межах:** T1–T10 окремо й у поєднаннях; некоректні дані (розд. 4); довідник станцій; склад і
формат чека; регресія змін v2 → v3.

**Поза межами:** надсилання чека на e-mail — рішення до 2026-11-30, на розрахунок не впливає
(`:159`–`:160`); купівля абонемента й підтвердження пільги — статус користувача є вхідними даними;
платежі, продуктивність, безпека, доступність — специфікація їх не описує.

### 1.4 Припущення та обмеження

- Моменти в API й тестах — ISO 8601 зі зсувом або `Z` (`AGENTS.md`); формат специфікація не
  визначає — Q-12.
- Частка копійки (`:129`–`:130`) за чинних цін наскрізно не виникає: блоки — цілі гривні (`:66`–`:67`),
  знижки 20 / 50 / 30 % (`:76`, `:86`, `:141`) дають цілі копійки. Округлення T9 перевіряється на
  рівні функції — прикладом `:137`.
- Поїздки через 00:00 чи 06:00 і T10 разом з T4 / T5 без оракула, доки немає відповідей на Q-1,
  Q-2, Q-10.

### 1.5 Зацікавлені сторони

Власник продукту (власник специфікації, `:9`) — відповідає на питання, затверджує план і звіт;
керівник служби експлуатації, фінансовий контролер, юрист громади (погоджували, `:10`); розробка;
тестування; служба підтримки (працює за специфікацією, `:16`).

## 4. Стратегія тестування

### 4.1 Підпроцеси тестування

| Рівень | Що | Де |
|---|---|---|
| Статичне | рев'ю специфікації → відкриті питання; тест-кейси й трасування | `docs/test-cases.md`, `docs/traceability.md` |
| Модульне | кожне правило ізольовано | `app/test/unit/`, `app/test/spec/` |
| Інтеграційне | `quote` + чек; HTTP API через `createHandler(deps)` без відкриття порту | `app/test/integration/`, `app/test/unit/server.test.js` |
| Системне / smoke | сервер піднімається, `GET /api/health` → 200 | крок smoke в CI (`ci/README.md`) |
| Якість тестів | мутаційне тестування, повтори набору | `tools/mutate.mjs`, `tools/repeat.mjs` |

### 4.2 Тестові артефакти

Тест-кейси й питання — `docs/test-cases.md` (99 кейсів, Q-1…Q-11); трасування — `docs/traceability.md`;
автотести зі специфікації з ID правила й TC-ID у назві — `app/test/spec/`; звіти про дефекти —
`docs/bugs/`; якість тестів — `docs/test-quality.md`; тріаж CI — `docs/triage.md`; правила для
агента, що пише тести, — `app/AGENTS.md`.

### 4.3 Техніки проєктування тестів

| Правило | Техніка | Чому |
|---|---|---|
| T1 (`:45`–`:47`), T2 (`:54`), T3 (`:62`), T8 (`:119`) | BVA: на межі й на кроці за нею (секунда) | ступінчасті функції з порогами |
| T4 (`:74`–`:77`) | класи за типом велосипеда + BVA 45 / 46 хв | різні правила для класичного й електро |
| T5 (`:89`–`:91`) | таблиця рішень | три результати порівняння й пріоритет абонемента |
| T6 (`:100`–`:103`) | сценарії зі станом журналу + BVA на 300 грн і на межі доби | сума накопичується між поїздками |
| T7, додаток А (`:111`–`:112`, `:164`–`:176`) | повний перебір 11 кодів + невідомий код | довідник малий |
| T9 (`:129`–`:137`) | приклади специфікації; точне порівняння сум | формат визначено, підписи — ні |
| T10 (`:141`) | класи «цілком уночі / удень»; межі — після Q-1, Q-10 | правило неоднозначне |
| Розд. 4 (`:147`–`:149`) | класи еквівалентності для негативних випадків | кожна підстава — окремий клас |

Очікуване — літерал зі специфікації, не з коду (`app/AGENTS.md`, правила 1–3).

### 4.4 Критерії входу та завершення

**Вхід:** специфікація затверджена (`:6`); `npm test` зелений на `main`; відповіді на Q-1, Q-2, Q-10 —
або письмова згода власника продукту тестувати T10 лише на поїздках цілком у вікні.

**Завершення** (усі разом):

| Критерій | Поріг | Зараз |
|---|---|---|
| Покриття правил | T1–T10, розд. 4, додаток А — у кожного пройдені автотести | так (`docs/traceability.md`) |
| Приклади специфікації | усі пройдено | так (`app/test/spec/`) |
| Мутаційний бал `tariff.js` + `day-cap.js` | ≥ 95 %; кожен живий мутант — еквівалентний з аргументом або прив'язаний до відкритого питання | 95,2 %, 4 живі: 2 еквівалентні, 2 — Q-6 (`docs/test-quality.md`, розд. 4) |
| Покриття рядків `src/` unit-тестами | ≥ 95 % | 97,27 % (`ai-runs/c-after.txt`) |
| Відкриті дефекти | критичних і високих — 0 | 0: BUG-1…BUG-5 виправлено; CI-1152 — зміна не злита |
| Нестабільність | 0 падінь у `node tools/repeat.mjs 50` | 0 з 50 (`ai-runs/d-repeat-after.txt`) |
| Відкриті питання | ті, що змінюють суму, закрито відповіддю або прийнято власником продукту як ризик | Q-1…Q-15 відкриті |

**Серйозність дефекту:** критична — неправильна сума «До сплати» чи збору; висока — правильна сума,
але рядки чека не відповідають `:133`–`:135`; середня — формат суми; низька — решта.

### 4.5 Метрики

Покриття правил; мутаційний бал і живі мутанти (`tools/mutate.mjs`); покриття рядків
(`npm run coverage`); падіння на 50 повторів (`tools/repeat.mjs`); дефекти за правилом і
серйозністю; відкриті питання та їх вік.

### 4.6 Вимоги до тестових даних

- Лише синтетичні дані (станції — додаток А, користувачі — `rider-N`).
- Моменти задає тест, із зсувом або `Z`; дати — з 2026-09-15 (`:8`); для доби й ночі — моменти, де
  київський час і UTC дають різну дату чи годину; перехід годинника — 25.10.2026 (TC-06).
- Межі — значення на межі й на кроці за нею; для тривалості — секунда.
- Без `Math.random()` у тестах із точним очікуваним: випадкові дані без seed дали нестабільний тест
  (`docs/triage.md`, розд. 1). Кожен тест створює свій журнал ліміту (`createDayCap()`).

### 4.7 Вимоги до тестового середовища

- Node 22.5+ (CI — Node 24 на Ubuntu 24.04, `ci/README.md`), `node --test`; **без npm-залежностей**
  (`AGENTS.md`) — бібліотеки property-based тестування не додаємо, перебір пишемо самі.
- Результат не залежить від TZ хоста: `src/kyiv-time.js` рахує київський час явно.
- Smoke-крок CI піднімає сервер на власному порту й перевіряє, що процес живий: порт 3000 на
  раннері вже був зайнятий (`docs/triage.md`, run-1147).
- `npm audit` має `continue-on-error`; його `##[error]` — не причина падіння (`docs/triage.md`).

### 4.8 Повторне та регресійне тестування

Кожен виправлений дефект — повторна перевірка тим самим тестом і коміт виправлення в звіті
(`docs/bugs/BUG-<N>.md`). Регресія: `npm test` на кожен PR у CI; `node tools/mutate.mjs` і
`node tools/repeat.mjs 50` — перед злиттям змін у `app/src/` чи тестах. Після нової редакції
специфікації — оновити `docs/traceability.md` і тести змінених правил.

### 4.9 Критерії призупинення та відновлення

Призупинити: червоний будь-який приклад специфікації; змінилася специфікація — тести змінених
правил до оновлення трасування; середовище не дає задати моменти часу. Відновити: виправлення
злито, `npm test` зелений, трасування оновлено.

### 4.10 Відхилення від стратегії організації

Організаційної стратегії в репо немає; цей план — єдине джерело.

## 5. Тестові активності та оцінки

Активності: рев'ю специфікації й питання; тест-кейси й трасування; автотести за правилами;
повторне тестування дефектів; мутаційне тестування й повтори; тріаж CI; звіти. Оцінки в людино-днях
дає команда — у специфікації їх немає.

## 6. Укомплектування

### 6.1 Ролі, активності, відповідальність

Тест-лід — план, ризики, звіти; тестувальник — тест-кейси, автотести, тріаж; розробник — модульні
тести й виправлення; власник продукту — відповіді на питання, приймання; фінансовий контролер —
суми, ліміт, округлення. Конкретних людей призначає команда.

### 6.2 Потреби в навчанні

Київський час і перехід годинника (`:37`, TC-06); техніки BVA і таблиць рішень; мутаційне
тестування й аналіз живих мутантів; читання логів CI.

## 7. Графік

Дати визначає команда (специфікація їх не містить). Зовнішня дата — 2026-11-30: рішення про e-mail
чека (`:159`–`:160`); якщо «надсилати» — переглянути межі (1.3).
