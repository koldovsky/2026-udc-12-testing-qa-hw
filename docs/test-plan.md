**Конвенція посилань.**

- `[Lnn]` / `[Lnn–mm]` — рядок / діапазон рядків файлу `docs/spec/tariffs.md` (версія 3). Кожне
  твердження про поведінку системи в цьому плані має таке посилання.
- `шлях:nn` — файл репо (код, тести, звіти). Так позначено твердження про **реалізацію**, а не про
  вимоги. Те, що код обрав там, де специфікація мовчить, — не очікування, а ВП (див. 1.4, A-6).
- **Рішення плану** — не твердження про систему, а вибір тест-плану (техніка, поріг, оцінка,
  графік). Посилання на специфікацію не потребує, але погоджується зацікавленими сторонами (розд. 2).
- **ВП-nn** — відкрите питання до специфікації (останній розділ). Тести, очікуваний результат яких
  залежить від ВП, мають статус «заблоковано» і не вигадують відповіді.
- Значення в прикладах — у гривнях; «стандартний / класичний / повернення на S01 / взяття вдень»,
  якщо не сказано інше.

## 1. Контекст тестування

### 1.1 Проєкт / рівень тестування

**Проєкт.** Реалізація розрахунку вартості поїздки за специфікацією тарифів версії 3, яка замінює
версію 2 від 2026-03-02 [L11]. Зміни v3 відносно v2: додано нічну знижку T10, денний ліміт
збільшено з 250 до 300 грн, збір за повернення поза зоною — 150 грн замість 100 грн [L151–155].

Специфікація — єдине джерело очікуваної поведінки для розробки, тестування і служби підтримки; за
розбіжності програми, чека чи відповіді оператора з документом правильним вважається документ
[L15–18]. Отже, кожна розбіжність реалізації зі специфікацією в цьому плані — дефект реалізації, а
не «особливість».

**Рівні тестування (рішення плану).**

### 1.3 Межі тестування

**У межах:**

- Правила T1–T10 [L43–143], некоректні дані §4 [L145–149], довідник станцій (додаток А) [L162–176].
- Склад і формат чека [L132–135].
- Усі приклади специфікації як приймальні тести (рішення плану).
- Взаємодія правил: T2×T7 [L55], T4×T5 [L89–91], T6×T4/T5/T10 [L100], T6×T7/T8 [L102–103, L120],
  T7×T8 [L121–122], T5×збори [L87].
- Регресія змін v3 відносно v2 [L151–155].

**Поза межами:**

- Автоматичне надсилання чека на e-mail — відкрите питання самої специфікації, яке не впливає на
  розрахунок вартості [L159–160].
- Оплата, повернення коштів, купівля абонемента, підтвердження права на пільгу: специфікація
  визначає лише терміни «Абонемент» і «Пільга» [L32–33], але не описує ці процеси.
- Розрахунок за правилами v2 (крім перевірки, що старі значення 250 грн і 100 грн не
  використовуються [L154–155]); застосовність v2 до перехідних поїздок — ВП-08.
- Нефункціональні характеристики (продуктивність, доступність, безпека, UI): у специфікації вимог
  до них немає (ВП-13). За потреби — окремий план.
- Ліміт T6 для **кількох** поїздок через HTTP API: `POST /api/quote` викликає `quote` без журналу
  ліміту (`app/src/server.js:33`), тобто кожна поїздка рахується так, ніби інших за добу не було.
  Ліміт на кількох поїздках тестується на компонентному рівні (`quote` + `createDayCap()`); чи має
  API враховувати попередні поїздки — питання до проєкту П-1 (розд. 1.4), ризик R-16.

## 3. Реєстр ризиків

Ймовірність і вплив — оцінка плану (рішення плану). Вплив «високий» = неправильна сума до сплати
(для кожної поїздки, якої це стосується) — за цим правилом оцінено **всі** рядки. Ймовірність
«висока» з позначкою «траплялося» — ризик уже реалізувався в цьому коді (`docs/bugs/`).

## 4. Стратегія тестування

### 4.1 Підпроцеси тестування

Рішення плану — підпроцеси за ISO/IEC/IEEE 29119-2:

1. **Планування** — цей документ; плани рівнів не створюються окремо, рівні описано в 1.1.
2. **Моніторинг і контроль** — щотижневі метрики (4.5), журнал ВП, повторна оцінка ризиків при
   кожній відповіді на ВП.
3. **Статичне тестування** — рецензування специфікації (результат — розділ «Відкриті питання»);
   рецензування тестових умов другою особою (оракул сум рахується вручну незалежно).
4. **Проєктування і реалізація тестів** — тестові умови → тест-кейси (додаток Б) → автотести.
5. **Підготовка середовища і даних** — 4.6, 4.7.
6. **Виконання** — автоматично в CI для компонентного й інтеграційного рівнів; системний і
   приймальний — за графіком (розд. 7).
7. **Звітування про інциденти** — з ID правила [L18–19].
8. **Завершення** — звіт про завершення, архів тестових даних, оновлена матриця трасування.

### 4.4 Критерії входу та завершення

**Критерії входу (рішення плану):**

- Специфікація v3 має статус «Затверджено» [L6] — виконано.
- ВП-01…ВП-04 (T10, сумування знижок, округлення, порядок порівняння T5) — відповідь власника
  продукту отримано або письмово зафіксовано прийняте тлумачення. До того — лише компонентне
  тестування незаблокованих умов.
- Збірка `app/` з `main`: `npm test` запускається на Node ≥ 22.5 без `npm install`

- Середовище з 4.7 готове: перевірено, що розрахунок дає ту саму київську добу за будь-якого
  `TZ` машини.

### 4.6 Вимоги до тестових даних

- **Користувачі** — лише синтетичні, без персональних даних; по одному на кожну категорію:
  стандартний, пільговий, абонент без права на пільгу, абонент із правом на пільгу [L38–39]; плюс
  другий стандартний для перевірки незалежності ліміту різних користувачів [L100].
- **Велосипеди** — класичний і електровелосипед [L38]; плюс недійсний тип для §4 [L148].
- **Станції** — усі 11 кодів додатка А [L166–176]; недійсні: `S09`, `X04`, порожній код (§4
  [L148–149]).
- **Моменти часу** — ISO 8601 з явним зміщенням (`+03:00`/`+02:00`), щоб уникнути неоднозначності
  локального часу; базова «звичайна» дата — 2026-09-16 (дата прикладу T6 [L105]), тобто після
  набрання чинності v3 [L8].
- **Межі** — тривалості з точністю до секунди для T1/T2 [L45–47, L54]; тривалості в хвилинах на
  межах 30/31, 45/46, 60/61, 75/76, 90/91, 105/106, 360/361, 1 440/1 441 (додаток Б).
- **Події в часі** — послідовності поїздок одного користувача протягом доби і через північ
  [L101–102, L107]; умовні дати переходу часу: 2026-10-25 і 2027-03-28 (ВП-11).
- **Оракул** — кожна очікувана сума в таблицях даних має посилання на рядок специфікації і
  перевірена другою особою.
- **Відтворюваність** — моменти взяття і повернення — літерали в тесті, а не «зараз» чи
  випадкові значення; `Math.random()` без зерна у визначальних даних заборонено (R-18; зараз
  лише `app/test/helpers/factory.js:10-11`); фіксоване зерно генератора для тестів властивостей;
  новий журнал `createDayCap()` на кожен тест.
- **Повний склад очікування** — для кожного кейсу не лише `total`, а й `minutes`, `timeCharge`,
  кожна знижка і кожен збір із сумою [L133–135]: тест, що рахує лише кількість зборів, пропустив би
  урізаний збір (`docs/bugs/CI-1152.md`, «Додатково»).

### 4.7 Вимоги до тестового середовища

- Node ≥ 22.5 (`package.json`, `engines`), без npm-залежностей і без `npm install` (O-3).
- Годинник не потрібен: моменти взяття і повернення — вхідні дані `quote` (A-3); тест ніколи не
  чекає реального часу.
- Часовий пояс: усі значення — за Europe/Kyiv [L37]. Код бере київську дату й годину через
  `Intl` з `timeZone: "Europe/Kyiv"` незалежно від поясу машини (`app/src/kyiv-time.js:1-11`), тож
  набір проганяється щонайменше з `TZ=UTC` і `TZ=Europe/Kyiv`, щоб помилка «доба за
  поясом машини» (R-07) не сховалася. Версія tzdata — та, що вбудована в Node (ВП-11).
- Довідник станцій — `app/src/zones.js`, звірений з додатком А [L162–176]; підміна — через
  `createZones()`.
- Журнал денних нарахувань — `createDayCap()` (`app/src/day-cap.js:12`), новий на кожен тест;
  історія за добу задається попередніми викликами `quote` з тим самим журналом.
- Чек — перевірка структури (`discounts`, `fees`) і тексту (`formatReceipt`, формат [L132–133]).
- Мережа: тести HTTP — через `createHandler()` без порту (`app/test/unit/server.test.js:6`) або
  `listen(0)`; жодного фіксованого порту 3000 у тестах (CI run-1147 упав через зайнятий порт,
  `docs/triage.md`, розд. 2).
- Автоматичний прогін у CI на кожну зміну (`ci/README.md`); жодних зовнішніх платіжних систем
  (поза межами, 1.3).

### 4.8 Повторне та регресійне тестування

- **Повторне (підтверджувальне)**: кожен виправлений дефект перевіряється тим самим тест-кейсом,
  що його виявив; тест-кейс залишається в регресійному наборі.
- **Регресійне**: увесь автоматичний набір (`npm test`, `npm run test:unit`,
  `npm run test:tools`) — на кожну зміну в CI. Обов'язкова частина — перевірки змін v3: ліміт
  300 грн [L154], збір 150 грн [L155], T10 [L153]; і тести на кожен виправлений дефект
  (`docs/bugs/README.md`).
- **Падіння в CI** — спершу тріаж за класом (код / тест / середовище / нестабільний,
  `docs/triage.md`), а не перезапуск: «зелений після перезапуску» не закриває інциденту (R-18).
- **Зміна специфікації**: при новій версії `docs/spec/tariffs.md` — оновлення матриці трасування,
  повторна оцінка ризиків, перегляд очікуваних сум усіх тестів, що посилаються на змінені рядки.
- **Відповідь на ВП**: розблоковані тести реалізуються і додаються до регресії.

### 4.9 Критерії призупинення та відновлення

| Призупинення (рішення плану) | Відновлення |
|---|---|
| Базові правила T1 або T3 дають неправильні суми в > 20 % тестів — подальші результати недостовірні | Виправлення, підтверджене компонентними тестами T1/T3 |
| Тестове середовище (CI-раннер, Node ≥ 22.5) недоступне > 1 робочого дня | Середовище відновлено, контрольний прогін пройдено |
| Нестабільний тест: хоч один червоний прогін у `node tools/repeat.mjs 50` | Причину знайдено й виправлено, повтор — 0 з 50 |
| Заблоковано > 30 % тестів системного рівня через відкриті ВП | Відповіді на ВП, що блокують, отримано |
| Специфікація змінюється під час циклу | Нова версія затверджена, матрицю трасування оновлено |

### 4.10 Відхилення від стратегії організації

Документа стратегії тестування організації в репо немає (O-1). Найближче до неї — правила репо
`AGENTS.md` (без npm-залежностей; `docs/spec/`, `ci/`, `tools/` не змінювати) і правила тестів
`app/AGENTS.md`, розд. «Тести». План їм відповідає; єдине свідоме відхилення від загальної
практики — тести властивостей без бібліотеки (O-3). Після отримання організаційної стратегії —
звірити й зафіксувати відхилення тут.
