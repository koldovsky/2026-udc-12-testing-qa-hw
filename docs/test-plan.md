## 2. Комунікація тестування
Періодичність і формати нижче — **[пропозиція]**, у специфікації їх немає.

| Хто → кому | Що | Як часто |
|---|---|---|
| Тестувальник → розробка | Дефекти з посиланням на правило `Tn` і рядок специфікації, приклад «вхід → очікувано/фактично» | Одразу |
| Тестувальник → власник продукту | Відкриті питання до специфікації (розділ нижче) | Одразу для блокерів, решта — раз на тиждень |
| Тестувальник → власник продукту, фінансовий контролер | Звіт: покриття правил, статус дефектів за серйозністю | Після кожного прогону регресії |
| Власник продукту → тестувальник | Рішення за ВП, нова версія специфікації | За потреби, до початку відповідного етапу |
| Тестувальник → служба підтримки | Підтверджені приклади розрахунку (довідник) | Після приймального прогону |

Рішення за відкритими питаннями фіксуються в новій версії специфікації, а не в усній домовленості.
Специфікація визначає ідентифікатори `T1`–`T10` як обов'язкові для посилань у задачах, тестах і зверненнях (S:L18-19).

## 4. Стратегія тестування

### 4.1 Підпроцеси тестування
- Планування й контроль: цей план, перегляд після рішень за відкритими питаннями.
- Аналіз і проєктування: правило за правилом, трасування `Tn` → тест-кейси.
- Реалізація: автотести «вхід → очікувана сума й вміст чека».
- Виконання й звітування: регресійний прогон, звіт за метриками з 4.5.
- Завершення: архів результатів, оновлення довідника прикладів для служби підтримки.

### 4.2 Тестові артефакти
- Тест-кейси, по одному принаймні на кожне правило й кожну межу.
- Матриця трасування: рядок специфікації / `Tn` → ідентифікатори тестів. Кожен тест має посилання на `Tn`.
- Автотести. Оракул — незалежна еталонна реалізація в цілих копійках або таблиця очікуваних значень, написана вручну за специфікацією, не з коду системи.
- Таблиця тестових даних (4.6).
- Звіти про прогони та реєстр дефектів.
- Реєстр відкритих питань до специфікації.

### 4.6 Вимоги до тестових даних

- Поїздки задаються моментами взяття й повернення з секундами та явною зоною Europe/Kyiv (S:L37).
- Межі:
  - тривалість: 0 с, 1 хв, 2 хв, 2 хв 1 с, 30 хв, 30 хв 1 с, 45 хв, 45 хв 1 с, 75 хв, 1 440 хв, 1 440 хв 1 с;
  - час доби: 23:59:59, 00:00:00, 05:59:59, 06:00:00;
  - ліміт _(виправлено)_: накопичення рівно 300,00 грн (120 + 120 + 60, S:L105-106) і наступна поїздка тієї ж доби → 0 погодинного; накопичення 275,00 грн + блок 25,00 грн → рівно 300,00 без зрізання; 300,00 + 1 блок → зрізання на весь блок.

- Багатоденні сценарії: поїздка через північ (S:L106-107), поїздка понад добу (S:L124).
- Дати переходу на літній/зимовий час — окремий набір, очікування блоковані до ВП-6.
- Відтворюваність: усі дані зафіксовані в репозиторії тестів, час у тестах не береться з годинника системи.

### 4.7 Вимоги до тестового середовища
_(виправлено: у чернетці «технології невідомі», «підміна годинника»)_
- Node 22.5+, вбудований раннер `node --test`, без npm-залежностей (`package.json`, `app/package.json`); команди — з
  кореня репо в Git Bash (`npm test`, `npm run coverage`, `npm run mutate`, `npm run test:repeat -- 50`).
- Підміна годинника не потрібна: `quote()` не читає поточний час, кожен тест задає моменти явно зі зміщенням
  (`+03:00` / `Z`); часова зона машини на результат не впливає (`app/src/kyiv-time.js` — `Intl` з `Europe/Kyiv`).
- Довідник станцій відповідає додатку А (S:L162-176) — `app/src/zones.js`.
- Для перевірки переходу на літній/зимовий час — ICU / tzdata, вбудовані в Node; версію фіксує `node --version`.
- HTTP-рівень — `createHandler()` без відкриття порту; для e2e — сервер на вільному порту (`listen(0)`), не на 3000
  (досвід прогону CI 1147 — `docs/triage.md`).

### 4.8 Повторне та регресійне тестування
- Повторне тестування: кожен виправлений дефект — повторення його кейса з посиланням на `Tn`.
- Регресія: повний набір автотестів у кожному прогоні CI (дешевий, оскільки модульний), системні сценарії чека й ліміту — у кожному релізі.
- Тригер повного прогону: будь-яка зміна констант (ціни, ліміт, збори) або нова версія специфікації.
  Історія змін показує, що саме константи змінювалися (S:L151-155).
- Тести, що залежать від ВП, розблоковуються й додаються до регресії після рішення.

### 4.9 Критерії призупинення та відновлення
- **Призупинити**, якщо:
  - збій у розрахунку блокує понад 30 % тестів (**[пропозиція]**);
  - з'ясувалося, що у системи інша версія тарифів, ніж v3;
  - середовище нестабільне (недетермінований час).
- **Відновити** після виправлення чи заміни збірки, успішного смоук-набору (приклади з 4.6) і повторного підтвердження версії тарифів.

### 4.10 Відхилення від стратегії організації
Стратегії організації не надано, тому відхилення не визначені.
Цей план — самодостатній, його положення треба буде звірити зі стратегією, коли її нададуть (ВП-17).

## 6. Укомплектування

### 6.1 Ролі, активності, відповідальність
- **Тест-аналітик:** аналіз специфікації, проєктування кейсів і матриці трасування, ведення ВП.
- **Автоматизатор тестування:** еталонний оракул, автотести, мутаційне тестування.

- **Фінансовий контролер:** узгодження очікуваних сум і правил округлення (S:L10).
- **Служба підтримки:** приймання довідника прикладів.

Один виконавець може поєднувати кілька ролей, але автор оракула не має бути автором коду розрахунку.
