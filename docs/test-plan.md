# Тест-план: розрахунок вартості поїздки Велопрокату громади, тарифи версії 3 (`app` 3.2.0)

> Task E (бонус, шлях 2). Виправлена чернетка AI `ai-runs/e-test-plan.md`; що саме виправлено
> і чому — `docs/task-e-bonus.md`. Структура — за розділами тест-плану ISO/IEC/IEEE 29119-3.
>
> **Посилання.** `spec:N` — рядок N файлу `docs/spec/tariffs.md` (версія 3). `файл:N` — рядок
> файлу репо. Твердження про систему без такого посилання тут не робляться. **[рішення плану]**
> позначено пороги, оцінки й порядок робіт: у специфікації їх немає, їх погоджує власник
> продукту. Усе, на що специфікація не відповідає, — у розділі «Відкриті питання до
> специфікації» (номери `Q-n` — ті самі, що в `docs/test-cases.md`).

## 1. Контекст тестування

### 1.1 Проєкт / рівень тестування

- **Реліз:** тарифи версії 3 (spec:5), статус «Затверджено» (spec:6), чинні з 2026-09-15
  (spec:8), замінюють версію 2 від 2026-03-02 (spec:11). Реалізація — `app/` версії 3.2.0
  (`app/package.json:3`).
- **Що змінилося у версії 3 (фокус регресії):** нове правило T10 — нічна знижка (spec:153);
  денний ліміт T6 — 300 грн замість 250 грн (spec:154); збір T7 — 150 грн замість 100 грн
  (spec:155).
- **Тестова основа:** специфікація — «єдине джерело очікуваної поведінки»; якщо програма чи
  чек розходяться з документом, правильним вважається документ (spec:15–18). Правила мають
  ID T1–T10, на них посилаються тести (spec:18–19).
- **Рівні тестування:**
  1. **Компонентний:** `quote` (`app/src/tariff.js:40`), журнал ліміту `createDayCap`
     (`app/src/day-cap.js`), київський час (`app/src/kyiv-time.js`), зони (`app/src/zones.js`),
     текст чека (`app/src/receipt.js`). Тести — `app/test/unit/` (24) і `app/test/spec/` (82).
  2. **Інтеграційний:** чек поїздки від `quote` до тексту (`app/test/integration/receipt.test.js`, 2
     тести).
  3. **Системний:** HTTP API `POST /api/quote` і `GET /api/health` (`app/src/server.js`, опис —
     `app/README.md:14`) і сторінка `app/public/index.html`. Тести API —
     `app/test/unit/server.test.js`: викликають `createHandler` без відкриття порту (`:4`, `:25`;
     `AGENTS.md:18`).
  4. **Приймальний:** приклади специфікації (spec:49–50, 57–58, 69–70, 81–82, 93–96, 105–107,
     114–115, 124–125, 137, 143) як приймальні тести, які погоджує власник продукту.

### 1.3 Межі тестування

**У межах:**

- Правила T1–T10 (spec:43–143) і їхні взаємодії: T2 і збір T7 (spec:55); вибір між T4 і T5
  (spec:89–91); ліміт T6 після знижок T4, T5, T10 і поїздка через північ (spec:100–103);
  незалежність T7 і T8 (spec:121–122); пільга не діє на збори (spec:86–87), ліміт їх не
  обмежує (spec:102–103).
- Обидва типи велосипедів і всі категорії користувачів (spec:38–39).
- Усі 11 кодів додатку А: S01–S08 у зоні, X01–X03 поза зоною (spec:164–176).
- Відхилення некоректних запитів (spec:147–149) — лише факт «відхилено, розрахунку немає»:
  текст пояснення не визначено (Q-11).
- Склад і формат чека (spec:132–135) — у межах того, що специфікація визначає однозначно.
- Київський час (spec:37) і межі доби (spec:34).

**Поза межами:**

- Надсилання чека на e-mail — відкрите питання служби підтримки, на розрахунок не впливає
  (spec:159–160).
- Видача й фіксація велосипеда станцією: моменти взяття й повернення — вхідні дані
  (визначення — spec:26–27).
- Оформлення абонемента й перевірка права на пільгу: категорія — вхідні дані (spec:32–33, 39).
- Оплата, продуктивність, безпека: вимог у специфікації немає.
- Тексти помилок, HTTP-коди і розмітка сторінки: специфікація їх не задає. Тести API
  перевіряють лише, що розрахунок збігається з `quote` і що некоректний запит відхилено
  (правило 12 чек-листа `docs/ai-test-checklist.md`).

## 4. Стратегія тестування

### 4.1 Підпроцеси тестування

1. **Статичне тестування специфікації** — рецензія `docs/spec/tariffs.md`: усі приклади
   (розд. 1.1) звірено з правилами; неоднозначності — Q-1…Q-12 і Q-15 (`docs/test-cases.md`).
2. **Проєктування кейсів зі специфікації** — `docs/test-cases.md`, трасування
   `docs/traceability.md`.
3. **Компонентне й інтеграційне тестування** — `npm test` (108 тестів: unit 24, spec 82,
   integration 2).
4. **Мутаційне тестування** — `npm run mutate` (`tools/mutate.mjs`) для `app/src/tariff.js` і
   `app/src/day-cap.js`; мутанти, що вижили, — тест або доказ еквівалентності
   (`docs/test-quality.md`, розділ 4).
5. **Перевірка стабільності** — `npm run test:repeat -- 50` (`tools/repeat.mjs`).
6. **Тріаж падінь CI** — `docs/triage.md`.
7. **Приймальне тестування** — приклади специфікації разом з власником продукту.
