Виправлена чернетка AI (`ai-runs/e-test-plan.md`); що саме виправлено і чому —
`docs/task-e-bonus.md`. Посилання `[tariffs.md:NN]` — рядки `docs/spec/tariffs.md`.

> Специфікація — єдине джерело очікуваної поведінки; у разі розходження
> правильним вважається документ [tariffs.md:15–18]. Кожне правило має
> ідентифікатор `T1`–`T10` [tariffs.md:18–19].

## 1. Контекст тестування

### 1.1 Проєкт / рівень тестування

- **Проєкт:** розрахунок вартості поїздки Велопрокату громади за специфікацією
  тарифів v3 [tariffs.md:5, 15]; реалізація — `app/` (veloprokat 3.2.0,
  `app/package.json`).
- **Пріоритет релізу:** зміни v3 — T6 (ліміт 250 → 300 грн), T7 (збір
  100 → 150 грн), нова T10 [tariffs.md:153–155] — тестуються першочергово.
- **Рівні тестування:**
  - **unit** — `quote()` і правила T1–T5, T7–T10 (`app/test/unit/`,
    `app/test/spec/`);
  - **інтеграційний** — денний ліміт T6 як стан між поїздками
    (`createDayCap`, [tariffs.md:100–101]), довідник станцій (додаток А,
    [tariffs.md:162–177]), чек разом із розрахунком (`app/test/integration/`);
  - **системний** — HTTP API (`POST /api/quote`, `app/src/server.js`) і склад
    чека [tariffs.md:132–135].
- Приймальний рівень — поза планом (власник продукту, [tariffs.md:9]).

### 1.2 Об'єкти тестування

- Логіка розрахунку T1–T10 — `app/src/tariff.js` [tariffs.md:41–143];
- денний ліміт — `app/src/day-cap.js` (доба за Києвом — `app/src/kyiv-time.js`)
  [tariffs.md:34, 100–103];
- довідник станцій — `app/src/zones.js` ↔ додаток А [tariffs.md:162–177];
- чек — `app/src/receipt.js` [tariffs.md:132–135];
- валідація некоректних даних — `readRide`/`readRider` у `app/src/tariff.js` і
  HTTP-шар `app/src/server.js` [tariffs.md:147–149];
- сторінка `app/public/index.html` — лише як клієнт API (смок).

### 1.3 Межі тестування

**У межах:** округлення тривалості вгору (T1) [tariffs.md:45–47]; хибний старт
≤ 2 хв (T2) [tariffs.md:54–55]; блоки по 30 хв, 25/40 грн (T3)
[tariffs.md:62–67]; абонемент — 45 безкоштовних хв на класичному, −20 % і без
безкоштовних хвилин на електро (T4) [tariffs.md:74–77]; пільга −50 %, не на
збори, вибір «пільга чи абонемент», нічия → абонемент (T5) [tariffs.md:86–91];
денний ліміт 300 грн, доба взяття за Києвом, збори поза лімітом (T6)
[tariffs.md:34, 100–103]; збір 150 грн поза зоною (T7) [tariffs.md:111–112];

цілі копійки, округлення вниз, формат чека (T9) [tariffs.md:129–135]; нічна

[tariffs.md:147–149]; типи велосипедів і категорії користувачів
[tariffs.md:38–39].

**Поза межами:** e-mail-чеки (відкрите питання специфікації, «на розрахунок не
впливає» [tariffs.md:159–160]); оформлення абонементів і підтвердження пільги
(специфікація задає лише наслідки статусів [tariffs.md:32–33]); апаратна
фіксація взяття/повернення [tariffs.md:26–27]; платежі; навантажувальне й
безпекове тестування (окремі плани).

### 1.4 Припущення та обмеження

- Усі значення часу — за київським часом (Europe/Kyiv), якщо не сказано інше
  [tariffs.md:37–38]; тести задають моменти ISO 8601 з явним зсувом і не
  залежать від системної зони CI.
- Тестуємо лише v3 (чинна з 2026-09-15, замінює v2 [tariffs.md:5–11]); зворотна
  сумісність із v2 не перевіряється.
- Усе, на що специфікація не відповідає, — у «Відкритих питаннях» нижче, не у
  припущеннях; відповідні тести не пишуться або явно позначаються як фіксація
  поточної поведінки з номером питання (правило 8 `app/AGENTS.md`).

### 1.5 Зацікавлені сторони

## 4. Стратегія тестування

### 4.1 Підпроцеси тестування

1. **Статичне тестування специфікації** — рецензування; результат — «Відкриті
   питання» (виконано: Q-1…Q-4 у `docs/test-cases.md` + ВП нижче).
2. **Unit/spec-тестування розрахунку** — набір на кожне правило, ID правила в
   назві тесту [tariffs.md:18–19] (`app/test/spec/`, `app/test/unit/`).
3. **Інтеграційне** — ліміт T6 між поїздками, чек разом із quote()
   (`app/test/integration/`).
4. **Системне** — HTTP API (`app/test/unit/server.test.js`; смок `/api/health`
   у CI на виділеному порту — урок run-1147, `docs/triage.md`).
5. **Мутаційне тестування** — `npm run mutate` (`tools/mutate.mjs`) як міра
   чутливості набору.
6. **Регресійне** — весь набір у CI (4.8).

### 4.2 Тестові артефакти

- тест-кейси зі специфікації — `docs/test-cases.md` (правило, техніка, рядок
  специфікації, пріоритет);
- матриця трасування «правило → кейси → автотести» — `docs/traceability.md`;
- автотести — `app/test/spec/*.test.js`, `app/test/unit/*.test.js`,
  `app/test/integration/*.test.js`;
- звіти: `npm run coverage`, `npm run mutate`, `npm run test:repeat`;
  журнал дефектів — `docs/bugs/` з прив'язкою до T-ідентифікаторів.

### 4.4 Критерії входу та завершення

**Вхід:** специфікація v3 затверджена [tariffs.md:6] ✓; код у репо і
збирається (`app/`, Node ≥ 22.5) ✓; довідник станцій доступний як дані
(`app/src/zones.js`) ✓; тести можуть задавати момент часу з явним зсувом і не
залежать від системної зони ✓.

**Завершення:**

- 100 % рядків матриці трасування (T1–T10 + розд. 4) мають щонайменше один
  зелений тест; кожен числовий приклад специфікації [tariffs.md:49–50, 57–58,
  69–70, 81–82, 93–96, 105–107, 114–115, 124–126, 137, 143] — окремий автотест;
- покриття рядків `app/src/tariff.js` і `app/src/day-cap.js` ≥ 95 % (фактично
  досягнуто 100 % — `ai-runs/c-after.txt`);
- мутаційний бал `npm run mutate` ≥ 90 % (фактично 97.6 %; 2 вцілілі мутанти
  аргументовано еквівалентні — `docs/test-quality.md` §4);
- стабільність: `npm run test:repeat -- 50` без жодного падіння
  (`ai-runs/d-repeat-after.txt`);
- 0 відкритих критичних/високих дефектів (що змінюють «До сплати»); середні —
  ≤ 3 і лише з погодженням фінансового контролера [tariffs.md:10];
- відкриті питання або закриті новою версією специфікації, або явно перенесені
  власником продукту [tariffs.md:9].

### 4.5 Метрики

Частка правил із зеленими тестами (ціль 100 %); частка прикладів специфікації
в тестах (100 %); покриття рядків/гілок; мутаційний бал; падінь на
`test:repeat -- 50` (0); дефекти за серйозністю і правилом; відкриті питання
та час їх закриття; тривалість прогону CI.

### 4.6 Вимоги до тестових даних

- синтетичні моменти з точністю до секунди (межі T1/T2) і мілісекунди (хвіст
  над цілою хвилиною);
- межі: 30-хвилинні блоки [tariffs.md:62]; 45/46 хв (T4); рівно 300 грн (T6);
  рівно 24 год (T8); 00:00 і 06:00 (T10); рівність «абонемент = пільга» (T5);
- події в часі: поїздка через північ за Києвом [tariffs.md:107]; послідовності
  поїздок доби [tariffs.md:105–106]; моменти, де київська і UTC-доба різні;
- довідникові: всі 11 кодів додатка А + неіснуючий код;
- **відтворюваність: жодних `Math.random` і поточного часу в тестах** — лише
  фіксовані ISO-моменти з явним зсувом (правило 6 `app/AGENTS.md`; урок
  флакі-тесту — `docs/triage.md`, розд. 1).

### 4.7 Вимоги до тестового середовища

Node ≥ 22.5, вбудований раннер `node --test`, без npm-залежностей; грошова
арифметика — точні цілі копійки [tariffs.md:129], без епсилон-порівнянь;
обчислення київського часу — через `Intl` (`app/src/kyiv-time.js`), тести
незалежні від системної зони; HTTP-тести — через `createHandler(deps)` без
відкриття порту; смок у CI — на виділеному порту з перевіркою тіла відповіді
(урок run-1147).

### 4.8 Повторне та регресійне тестування

Кожен дефект закривається тестом, що його відтворює (BUG-1…BUG-5 → spec-тести
TC-03/05/06/15/19/22), тест лишається назавжди; весь набір — у CI на кожен
push; ядро регресії — еталонні приклади специфікації і тести змін v3
[tariffs.md:153–155]; стабільність контролюється `tools/repeat.mjs`; при зміні
специфікації спершу оновлюються очікування тестів, потім код.

### 4.9 Критерії призупинення та відновлення

**Призупинення:** збірка не проходить; суперечність специфікації блокує ≥ 2
правила; хибні суми в базових T1/T3 — аналіз залежних правил (T4–T6, T10)
призупиняється, бо їхні очікування будуються на T3 [tariffs.md:30].
**Відновлення:** збірка зелена; відповідь власника продукту зафіксована новою
версією специфікації; базові правила зелені.

### 4.10 Відхилення від стратегії організації

Відхилень немає. Особливість: очікувані значення тестів — **тільки** зі
специфікації [tariffs.md:15–18], ніколи з поведінки коду (правила 1 і 4
`app/AGENTS.md`).

Адресат — власник продукту [tariffs.md:9]. До відповіді тести з цих випадків
не пишуться (або позначаються як фіксація поточної поведінки з номером
питання). ВП-1…ВП-4 збігаються з Q-1…Q-4 у `docs/test-cases.md`.

   лише для пари «пільга + абонемент» [tariffs.md:89–90], а термін «погодинне
   нарахування» перелічує T4, T5, T10 разом [tariffs.md:30]. Порядок впливає на

   відхиляється лише повернення **раніше** взяття [tariffs.md:147–148] — чи
