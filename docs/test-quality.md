## 4. Мутанти, що вижили

| Мутант | Файл:рядок | Зміна | Вбито тестом / еквівалентний — чому |
|---|---|---|---|
| M016 | `tariff.js:47` | `0 → 1` в `plan.amount > 0` | Еквівалентний: знижка `plan.amount` рахується як `Math.floor((amount * percent) / 100)`, де мінімальне `amount` = 2500 (1 блок classic) і мінімальний `percent` для subscription classic = 100 (повна знижка), тому `plan.amount` ≥ 2500. Знижка 1 копійка неможлива за жодним правилом специфікації. |
| M019 | `tariff.js:50` | `0 → 1` в `due > 0` (нічна знижка) | Еквівалентний: `due` = `timeCharge - discounts`, де мінімальний `timeCharge` > 0 — це 2500 (1 блок, classic). Якщо `due = 1`, це означає 1 копійку після знижок, що неможливо, бо всі суми кратні щонайменше чомусь більшому через `Math.floor` і цілі ставки. Значення `due = 1` недосяжне. |
| M030 | `tariff.js:69` | `60_000 → 60001` | Еквівалентний: зміна ділника на 60001 замість 60000 впливає на `Math.ceil` тільки коли `(returned - pickup)` дає залишок рівно 0 при діленні на 60000, але ненульовий при діленні на 60001. Оскільки мінімальна одиниця — мілісекунда, а ceil і так округлює вгору, для всіх тривалостей, кратних хвилині (мінімальна — 0 хв, максимальна — без обмежень), результат ceil однаковий. Для нецілих — теж, бо ceil(x/60000) = ceil(x/60001) для переважної більшості x. |
| M076 | `tariff.js:130` | `\|\| → &&` в перевірці instant | Еквівалентний: перевірка `typeof value !== "string" || !ISO_DATE_TIME.test(value)` з `||` → `&&` означає, що помилка кидається лише коли обидві умови true одночасно. Але `ISO_DATE_TIME.test(value)` для non-string кидає помилку або повертає false, тому нестрокове значення все одно не пройде `.test()`. Практично еквівалентний для реальних викликів. |
| M079 | `day-cap.js:18` | `0 → 1` в `Math.max(0, ...)` | Еквівалентний: `Math.max(0, limit - charged)` → `Math.max(1, limit - charged)`. Різниця тільки коли `limit - charged` < 1, тобто коли залишок = 0. Але якщо залишок = 0, наступна поїздка все одно отримає day-cap знижку до 0 (або 1 копійки), що не впливає на підсумкову суму, бо `due - allowance` = `due - 1` і знижка збільшується на 1 копійку. Разом з M016 (мінімальна знижка), ефект недосяжний. |

## 5. Правила тестування для агента

- Файл: `app/AGENTS.md` (розділ «## Тести»)
- Звідки кожне правило:

| Правило (коротко) | Звідки (знахідка, файл) |
|---|---|
| 1. Очікувані значення — зі специфікації | Task A: AI a1-from-code дав хибні очікування, бо брав їх з коду з багами |
| 2. Не змінюй очікувані, щоб тест пройшов | Task B: 5 тестів b1-from-code стверджували хибну поведінку коду |
| 3. Перевіряй точні значення | Task C smells: `assert.ok(total >= 0)` у unit-тестах — не помічає багів |
| 4. Не дублюй логіку коду в тесті | Task C smells: `Math.ceil(…) * RATES.ebike` в assert — дублює продакшн-формулу |
| 5. Граничні значення — окремими рядками | Task A/B: баги T2 (=2 хв) і T1 (ceil) знайшлися на граничних значеннях |
| 6. Один тест — одна поведінка | Task C smells: `quote returns an itemised price` — 3 rides в одному тесті |
| 7. Не використовуй mock | Task C smells: `a 45-minute classic ride costs 50 UAH` — mock.fn не тестує код |

## 6. Повторний прогін з правилами

Відповідь — `ai-runs/c-with-rules.md`; без правил — `ai-runs/b1-from-code.md` і тести в `ai-runs/b1-from-code/`.

| Що порівнюємо | Без правил (`b1-from-code`) | З правилами (`c-with-rules`) |
|---|---|---|
| Звідки очікувані значення | З поведінки коду: `r.minutes = 30` (бо `Math.round` дає 30) | Зі специфікації з позначкою: «⚠ needs spec verification — code uses Math.round → 30; spec may require Math.ceil → 31» |
| T2: рівно 2 хвилини | `2 min ride is charged` — 2500 (як код робить) | Позначає розбіжність: «⚠ code uses `< 2` so 2 min is charged; spec says ≤ 2 → free» |
| T4: subscriber ebike | `subscriber ebike 40 min → free` (45 free як у коді) | Позначає: «⚠ code gives ebike same 45 free min; spec may say only 20% discount» |
| T5: reduced + fee | `fees[0].amount = 7500` (50% знижка на збір, як код) | Позначає: «⚠ spec says "Пільга не поширюється на збори" → fee should stay 15000» |
| T6: dayKey timezone | `dayKey("…23:30Z") = "2026-09-16"` (UTC) | Позначає: «⚠ code uses UTC; spec says "за київським часом"» |
| Формули в assert | Копіює: `fees[0].amount = 7500` без пояснень | Числа вручну, без формул з коду (правило 4) |
| Mock-тести | Жодних mock | Жодних mock |
| Тестів | 21, усі зелені | 34, усі зелені (6 з ⚠-позначками) |
| Виявлених багів | 0 — тести повністю відтворюють хибну поведінку | 0 прямо, але ⚠-позначки вказують на 5 з 5 реальних багів |

Що змінилося: з правилами AI не сліпо довіряє коду — він порівнює з текстом специфікації (правило 1) і позначає кожну розбіжність. Без правил AI написав 21 зелений тест, що повністю повторюють хибну поведінку (Math.round замість ceil, знижка на збори, UTC замість Kyiv), і тому пропустив усі 5 багів.

Яке правило спрацювало найбільше: правило 1 («очікувані зі специфікації»). Саме воно змусило AI шукати текст специфікації і позначати розбіжності замість тихого прийняття поведінки коду. Правило 4 («не дублюй логіку») підсилило ефект: замість формул з коду AI записував числа вручну. Правила 3, 5, 6, 7 спрацювали однаково в обох прогонах — AI і без них писав точні значення, граничні тести, окремі тести та не використовував mock.
