# BUG-5: Денний ліміт розділяється за UTC-добою замість київської дати

| Поле | Значення |
|---|---|
| **Правило специфікації** | T6: «Сума погодинних нарахувань одного користувача за одну добу (після знижок T4, T5, T10) не перевищує **300 грн**. Поїздка належить до тієї доби, на яку припадає момент її **взяття** за київським часом, навіть якщо вона завершилася наступної доби. Збори в ліміт не входять і ним не обмежуються.» — `docs/spec/tariffs.md:100–103` |

| **Серйозність** | висока: на межі UTC-дати система може дозволити стягнути понад денний ліміт 30000 коп. за одну київську дату |
| **Частота** | завжди для записів у той самий київський день, якщо їхні UTC-інстанти потрапляють у різні UTC-дати |
| **Знайдено** | уточнений `app/test/spec/day-cap-and-receipt.test.js` › TC-13 T6; також B1 тести `dayKey uses the UTC calendar date…` та `ledger separates riders and pickup days` стали червоними в `ai-runs/b1-rerun.txt:47-89` |
| **Виправлення** | `295a721` — `fix(T6): key daily cap by Kyiv date` |

## Кроки відтворення

1. Створити копію початкового коду: `mkdir -p ../ws12-main && git archive main app | tar -x -C ../ws12-main`.
2. Для rider `r1` записати 24000 коп. о `2026-09-16T00:10:00+03:00`.
3. Порахувати ebike-поїздку того самого користувача з `2026-09-16T23:40:00+03:00` до `2026-09-17T00:20:00+03:00`.

## Очікуваний результат (за специфікацією)

Обидва моменти взяття припадають на 16.09 за Києвом. До ліміту 30000 коп. вже використано 24000, отже з 8000 коп. погодинної суми можна стягнути лише залишок 6000 коп. (`docs/spec/tariffs.md:100-103`).

## Фактичний результат

Початковий `dayKey` утворює ключі за UTC-датами: перший запис потрапляє в 15.09 UTC, а перевірювана поїздка — в 16.09 UTC. Ledger бачить повний новий ліміт і стягує 8000 коп.

## Мінімальний вхід

Два записи одного rider на один київський день: попередній у 00:10+03, перевірюваний у 23:40+03. Їхні UTC-дати різні, тому початковий ledger помилково вважає це різними днями.

## Додатково

`dayKey` тепер отримує дату з `kyivTime`. Перший автоматизований TC-13 мав попередній запис о 09:00 і не відрізняв UTC-групування від київського; вхід уточнено до 00:10, після чого дефект відтворився.
