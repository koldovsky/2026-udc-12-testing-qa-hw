# BUG-5: Денний ліміт рахується за UTC-добою, а не за київською

| Поле | Значення |
|---|---|
| **Правило специфікації** | T6 — «Доба — календарна дата за київським часом, від 00:00 до 24:00.» (`docs/spec/tariffs.md:34`); «Поїздка належить до тієї доби, на яку припадає момент її взяття за київським часом» (`:101-102`) |
| **Середовище** | `main` (початковий код) і коміт `24ccef0` (після виправлення); Node v26.13.0; Darwin 25.6.0 |
| **Серйозність** | середня — поїздки з 00:00 до 03:00 за Києвом літом (до 02:00 взимку) потрапляють у іншу добу ліміту, ніж решта київського дня; користувач може заплатити понад 300 грн за добу, а ліміт нічних поїздок не спрацьовує |
| **Частота** | за умови: київський час взяття 00:00–03:00 (літо) або 00:00–02:00 (зима) і попередні нарахування того ж київського дня |
| **Знайдено** | `app/test/spec/cap-and-fees.test.js` › `T6: TC-45 day is Kyiv's, not UTC …` (червоний лише після виправлення TC-45 людиною — у `ai-runs/b2-run.txt` він був зелений: хелпер записував попереднє нарахування тим самим моментом, що й поїздку; див. `docs/bugs/README.md`) |
| **Виправлення** | коміт `24ccef0` (`git log --oneline -1 24ccef0`) |

## Кроки відтворення

1. З кореня репо виконати команду з розділу «Доказ» — на копії початкового коду з `main` (`mkdir -p ../ws12-main && git archive main app | tar -x -C ../ws12-main && cd ../ws12-main`).
2. Порівняти вивід з очікуваним.
3. Виконати ту саму команду в репо після виправлення (`24ccef0`) — вивід збігається з очікуваним.

## Очікуваний результат (за специфікацією)

попередньо за київську добу 17.09 нараховано 29500 (о 00:05 +03:00); поїздка 17.09 03:30 +03:00: ціна 2500 − 30 % = 1750, залишок ліміту 500 → 500 коп (`docs/spec/tariffs.md:34`, `:100-102`, `:141`).

## Фактичний результат

`discounts: [{night, 750}]`, `total: 1750`: ліміт не спрацював — поїздка (UTC 17.09) і попереднє нарахування (UTC 16.09) опинилися в різних добах.

## Доказ

```bash
node --input-type=module -e '
import { quote } from "./app/src/tariff.js";
import { createDayCap } from "./app/src/day-cap.js";
const dayCap = createDayCap();
dayCap.record("u1", "2026-09-17T00:05:00+03:00", 29500);
const r = quote({ pickupAt: "2026-09-17T03:30:00+03:00", returnAt: "2026-09-17T03:50:00+03:00", bike: "classic", returnStation: "S01" },
  { type: "standard", id: "u1" }, { dayCap });
console.log(JSON.stringify(r));'
```

До виправлення (початковий код з `main`):

```text
{"minutes":20,"timeCharge":2500,"discounts":[{"code":"night","amount":750}],"fees":[],"total":1750}
```

Після виправлення (`24ccef0`):

```text
{"minutes":20,"timeCharge":2500,"discounts":[{"code":"night","amount":750},{"code":"day-cap","amount":1250}],"fees":[],"total":500}
```

## Мінімальний вхід

два записи в одну київську добу, один з яких з київським часом 00:00–03:00 (UTC попереднього дня).

## Додатково

Тести з коду, що стверджували хибну поведінку: `ai-runs/b1-from-code/day-cap.test.js` › `returns the UTC date as YYYY-MM-DD`, `normalises offsets to UTC`. Не плутати з HT-02 з A1 (`server.js` не підключає журнал ліміту) — окреме питання, не дефект за цим правилом, див. `docs/bugs/README.md`. Гіпотеза: `app/src/day-cap.js:7`, `toISOString().slice(0, 10)` → київська дата.
