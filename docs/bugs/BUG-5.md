# BUG-5: денний ліміт рахується за добою UTC — нічна поїздка після 00:00 за Києвом потрапляє у вчорашній ліміт

| Поле | Значення |
|---|---|
| **Правило специфікації** | T6 — «Поїздка належить до тієї доби, на яку припадає момент її **взяття** за київським часом» (`docs/spec/tariffs.md:101-102`); «Доба — календарна дата за київським часом, від 00:00 до 24:00» (`:34`) |
| **Середовище** | дефект — у `main` (`4606c72`), відтворено на копії `git archive main app`; Node v26.3.0; Windows 10 (Git Bash) |
| **Серйозність** | висока — користувач, який вичерпав ліміт увечері, отримує нічні поїздки 00:00–03:00 (влітку; 00:00–02:00 взимку) безкоштовно (недобір); і навпаки, поїздки 00:00–03:00 з'їдають ліміт попередньої доби, а нова доба отримує ще 300 грн — денний ліміт не діє як визначено |
| **Частота** | завжди для поїздок, взятих між 00:00 і 03:00 (EEST) / 02:00 (EET) за Києвом, коли в ту ж UTC-добу є інші поїздки користувача |
| **Знайдено** | `app/test/spec/tariff.test.js` › `T6: TC-35 17.09 00:30–01:00 за Києвом — нова доба: 2500 − 30 % = 1750` (`ai-runs/b2-run.txt`) |
| **Виправлення** | `1b3e725 fix(T6): book the daily cap on the Kyiv calendar date of pickup, not the UTC date` |

## Кроки відтворення

1. На коді з `main` створити журнал `createDayCap()` і провести через `quote` три поїздки
   електровелосипедом одного користувача 16.09: 09:00–10:20, 13:00–14:20, 18:00–19:20 за
   Києвом (`06:00Z`, `10:00Z`, `15:00Z`) — разом 30000, ліміт 16.09 вичерпано.
2. Тим самим журналом порахувати поїздку класичним велосипедом 17.09 00:30–01:00 за Києвом
   (`2026-09-16T21:30:00Z` → `2026-09-16T22:00:00Z`).

## Очікуваний результат (за специфікацією)

Взяття 17.09 00:30 за Києвом → поїздка належить до 17.09 (T6, `:101-102`; «Доба», `:34`), ліміт
17.09 не використано. 30 хв → 2500 (T3); уся поїздка в 00:00–06:00 → −30 % (T10, `:141`) →
до сплати **1750**, рядка «денний ліміт» немає.

## Фактичний результат

`discounts: [night 750, day-cap 1750]`, `total: 0` — поїздку записано на 16.09 (UTC-дата
`2026-09-16`).

## Доказ

```bash
node -e 'Promise.all([import("./app/src/tariff.js"), import("./app/src/day-cap.js")]).then(([{ quote }, { createDayCap }]) => {
  const dayCap = createDayCap(); const rider = { id: "r1", type: "standard" };
  const r = (a, b, bike) => ({ pickupAt: a, returnAt: b, bike, returnStation: "S01" });
  for (const [a, b] of [["06:00", "07:20"], ["10:00", "11:20"], ["15:00", "16:20"]])
    quote(r(`2026-09-16T${a}:00Z`, `2026-09-16T${b}:00Z`, "ebike"), rider, { dayCap });
  console.log(JSON.stringify(quote(r("2026-09-16T21:30:00Z", "2026-09-16T22:00:00Z", "classic"), rider, { dayCap })));
})'
```

До виправлення (копія `main`):

```text
{"minutes":30,"timeCharge":2500,"discounts":[{"code":"night","amount":750},{"code":"day-cap","amount":1750}],"fees":[],"total":0}
```

Після виправлення (`1b3e725`):

```text
{"minutes":30,"timeCharge":2500,"discounts":[{"code":"night","amount":750}],"fees":[],"total":1750}
```

## Мінімальний вхід

`dayKey("2026-09-16T21:30:00Z")` → `2026-09-16` (має бути `2026-09-17`). Будь-яке взяття о 09:00
за Києвом і пізніше до 24:00 дає ту саму дату в UTC і в Києві — дефект зникає.

## Додатково

- Місце в коді: `app/src/day-cap.js:6-8` (`dayKey`) — `new Date(pickupAt).toISOString().slice(0, 10)`
  (дата UTC); виправлено на `kyivTime(pickupAt).date` (`app/src/kyiv-time.js`).
- Наявні unit-тести дефект не стверджували: `the day of a ride is the date of its pickup`
  перевіряє 08:00Z (11:00 за Києвом), де дати UTC і Києва збігаються.
- Тест з коду `ai-runs/b1-from-code/day-cap.test.js` › `dayKey returns the UTC date of the
  instant` стверджував дефект прямо («01:00 Kyiv time … is still the 15th in UTC»).
- Той самий дефект побачили A1 (кейси G10/G11 з ⚠) і AI-тріаж CI (`ai-runs/d-ci-first.md`,
  «Побічне спостереження»), але як «підозру», бо специфікації не бачили.
