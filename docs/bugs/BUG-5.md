# BUG-5: денний ліміт рахується за добою UTC, а не за київським часом — нічні поїздки потрапляють у ліміт попереднього дня

| Поле | Значення |
|---|---|
| **Правило специфікації** | Термін «Доба — календарна дата за київським часом, від 00:00 до 24:00» (`docs/spec/tariffs.md:34`); T6: «Сума погодинних нарахувань одного користувача за одну добу … не перевищує 300 грн. Поїздка належить до тієї доби, на яку припадає момент її **взяття** за київським часом» (`:100-102`) |
| **Середовище** | Дефект: `main` = `4606c72` (код `app/src/` ідентичний `5468fe7`). Перевірка виправлення: `9623f08`. Node v22.14.0, macOS 26.4.1. Результат не залежить від часового поясу машини: ключ доби брався з `toISOString()` (UTC) |

Порушує правило, яке видно в чеку |
| **Частота** | Завжди для поїздок, взятих від 00:00 до 03:00 за Києвом влітку (UTC+3) або від 00:00 до 02:00 взимку (UTC+2), коли розрахунок іде з денним леджером (`dayCap`) |

## Кроки відтворення

1. Взяти копію початкового коду: `mkdir -p ../ws12-main && git archive main app | tar -x -C ../ws12-main`.
2. Один денний леджер (`createDayCap()`), один стандартний користувач `r1`, у порядку взяття
   (сценарій TC-48):
   - електровелосипед 16.09.2026, 08:00 → 15:00 за Києвом: 14 блоків, ліміт 16.09 вичерпано;
   - класичний 17.09.2026, 00:30 → 01:00 за Києвом (= 16.09 21:30 UTC).
3. Запустити команду з розділу «Доказ» у `../ws12-main`, а потім у корені репо.

## Очікуваний результат (за специфікацією)

- **Перша поїздка:** 56 000 → ліміт → **30 000**.
- **Друга поїздка:**
  - Взята 17.09 о 00:30 за Києвом, тож належить добі **17.09** (`:34`, `:101-102`), де ліміт
    ще не використано.
  - Уся поїздка в 00:00–06:00: 2 500 − 30 % (`:141`) = **1 750**.
- Ключ доби для `2026-09-17T00:30:00+03:00` — `2026-09-17`.

## Фактичний результат

Ключ доби для другої поїздки — **`2026-09-16`** (UTC-дата). Поїздку зараховано до вичерпаного
ліміту 16.09, тож `total` **0** замість 1 750.

## Мінімальний вхід

`dayKey("2026-09-17T00:30:00+03:00")`: код дає `"2026-09-16"` замість `"2026-09-17"`. Дефект
зникає, якщо взяття о 03:00 або пізніше за Києвом влітку (о 02:00 або пізніше взимку): тоді
UTC-дата збігається з київською.

## Додатково

- **Місце в коді:** `app/src/day-cap.js:7`, `dayKey()` — `new Date(pickupAt).toISOString().slice(0, 10)`.
  Виправлено в `9623f08`: `kyivTime(pickupAt).date` з `app/src/kyiv-time.js`. Ця сама функція
  вже визначала київську годину для нічної знижки (T10).
- **Наявні тести в `app/test/unit/`:** після виправлення не почервоніли. `dayKey("2026-09-16T08:00:00Z")`
  дає `2026-09-16` і за UTC, і за Києвом.
- **Тести з коду, що зафіксували дефект:** усі три мали в назві «(current behaviour)» і були
  зелені в `b1-run.txt`, червоні в `b1-rerun.txt`:
  - `ai-runs/b1-from-code/day-cap.test.js` › `dayKey` › `uses the UTC calendar date (current behaviour)`;
  - `ai-runs/b1-from-code/day-cap.test.js` › `createDayCap` › `instants on either side of UTC midnight land on different days`;
  - `ai-runs/b1-from-code/tariff.test.js` › `quote: daily cap with a ledger` › `books by UTC date (current behaviour)`.
- **Окремо, не цей дефект:** HTTP API (`app/src/server.js:33`) викликає `quote()` без
  `dayCap`. Через API денний ліміт між поїздками одного користувача не накопичується взагалі.
  Жоден червоний тест цього не показав; варто винести окремим питанням або дефектом.
