# Тест-кейси: розрахунок вартості поїздки (виведено з коду)

**Джерело:** лише файли з `app/src/` ([tariff.js](../app/src/tariff.js), [day-cap.js](../app/src/day-cap.js), [kyiv-time.js](../app/src/kyiv-time.js), [zones.js](../app/src/zones.js), [receipt.js](../app/src/receipt.js), [server.js](../app/src/server.js)).

**Важливе обмеження.** Код посилається на специфікацію `docs/spec/tariffs.md` (правила T3, T6, T9, додаток А). За умовою завдання я її не читав. Тому всі очікування нижче описують **поточну поведінку коду**, а не правильну за специфікацією. Такий набір тестів зафіксує нинішню поведінку (регресійні тести), але сам по собі не знайде місць, де код розходиться зі специфікацією. Кейси, де поведінка коду виглядає сумнівною і її треба звірити зі специфікацією, позначені ⚠ і зібрані в розділі «Що звірити зі специфікацією» в кінці.

Очікування я розрахував вручну за кодом. Потім перевірив арифметику: тимчасовий скрипт поза проєктом викликав `quote()` / `discount()` / `createHandler()` з наведеними вхідними даними. Усі значення в таблицях збігаються з тим, що повертає код.

## 1. Модель розрахунку (як її реалізує код)

`quote(ride, rider, { zones, dayCap })` → `{ minutes, timeCharge, discounts[], fees[], total }`, усе в копійках ([tariff.js:40-68](../app/src/tariff.js#L40-L68)).

1. **Хвилини** `minutes = Math.round((returnAt − pickupAt) / 60 000)`. Округлення до найближчої хвилини, рівно 30 с округлюються вгору ([tariff.js:70-72](../app/src/tariff.js#L70-L72)).
2. **Погодинне нарахування** (T3): якщо `minutes < 2`, то 0. Інакше `ceil(minutes / 30) × ставка`. Ставка за блок: classic = 2500, ebike = 4000 ([tariff.js:18-20](../app/src/tariff.js#L18-L20), [78-81](../app/src/tariff.js#L78-L81)).
3. **Тарифна знижка** (одна, та, що дає найбільшу знижку; [tariff.js:89-98](../app/src/tariff.js#L89-L98)):
   - `subscription`, лише для `rider.type = "subscriber"`: абонент платить `ceil(max(0, minutes − 45) / 30) × ставка`, для ebike ще −20% ([tariff.js:83-86](../app/src/tariff.js#L83-L86)). Знижка = `timeCharge − ця сума`.
   - `reduced`, для `type = "reduced"` або для `subscriber` з `concession === true`: 50% від `timeCharge`.
   - Нульова знижка в `discounts` не потрапляє. При рівних знижках перемагає та, що стоїть у списку раніше: `subscription` (строге `>` у [tariff.js:97](../app/src/tariff.js#L97)).
4. **Нічна знижка**: якщо залишок > 0 і година **посадки** за київським часом < 6, то −30% від залишку ([tariff.js:50-54](../app/src/tariff.js#L50-L54), [kyiv-time.js](../app/src/kyiv-time.js)).
5. **Денний ліміт** (T6) 30 000 ([day-cap.js:3](../app/src/day-cap.js#L3)). Без журналу ліміт рахується для кожної поїздки окремо. З журналом `createDayCap()` використовується залишок ліміту дня, і сума записується в журнал. День визначається датою посадки **за UTC** ([day-cap.js:6-8](../app/src/day-cap.js#L6-L8)). Код: [tariff.js:56-61](../app/src/tariff.js#L56-L61).
6. **Збори** (не потрапляють під нічну знижку і ліміт, у журнал не записуються; [tariff.js:105-110](../app/src/tariff.js#L105-L110)):
   - `out-of-zone` 15 000, якщо станція повернення має зону `out` (X01, X02, X03; [zones.js:3-15](../app/src/zones.js#L3-L15));
   - `unreturned` 200 000, якщо `minutes > 1440`.
   - Якщо обрано план `reduced`, кожен збір зменшується на 50% ([tariff.js:63-65](../app/src/tariff.js#L63-L65)).
7. **Округлення** (T9): `discount(a, p) = a − floor(a × (100 − p) / 100)`, тобто сума до сплати округлюється вниз до копійки ([tariff.js:101-103](../app/src/tariff.js#L101-L103)).
8. `total = залишок + Σ зборів`.

## 2. Типові вхідні дані

Якщо в кейсі не сказано інакше:

| Параметр | Значення |
|---|---|
| `P` (посадка, `pickupAt`) | `2026-06-15T10:00:00+03:00` (денний час Києва, літній час UTC+3) |
| `returnAt` | `P + тривалість`, з тим самим зсувом `+03:00` |
| `bike` | `"classic"` |
| `returnStation` | `"S01"` (зона `in`) |
| `rider` | `{ type: "standard" }`, без `concession`, без `id` |
| `zones` | за замовчуванням (`stationZones`, [zones.js:29](../app/src/zones.js#L29)) |
| `dayCap` | не передається (ліміт 30 000 на кожну поїздку окремо) |

Позначення в стовпці очікувань: `хв` = `minutes`, `T` = `timeCharge`, `зн.` = `discounts`, `зб.` = `fees`. Головна перевірка — **total** (виділено жирним).

## 4. Що звірити зі специфікацією (`docs/spec/tariffs.md`)

Тут код поводиться так, що це може бути як задумом, так і помилкою. Кейси вище фіксують поточну поведінку. Якщо специфікація каже інакше, очікування цих кейсів треба змінити.

1. **День для ліміту береться за UTC** (H05, H06). Поїздки з 00:00 до 02:59 (влітку) або до 01:59 (взимку) за Києвом записуються на попередній день. Нічна знижка при цьому рахується за київським часом, тобто в одній функції використано дві різні часові зони.
2. **Нічна знижка залежить лише від години посадки** і діє на всю поїздку (F05, G04, G05).
3. **Безкоштовна поїздка пільговика поза зоною**: збір 15 000 без зменшення, хоча за платну поїздку пільговик платить 7 500 (J02, J07). Причина: зменшення зборів прив'язане до обраного плану, а план `reduced` не обирається, коли знижка = 0.
4. **Нічия між абонементом і пільгою** вирішується на користь абонемента, тому збори не зменшуються (E02, E09). Для пасажира вигідніший був би `reduced`.
5. **`concession` має бути строго boolean `true`** (E04).
6. **Округлення тривалості `Math.round`**: 1 хв 30 с уже платні (A04), а 24 год 0 хв 30 с уже дають збір 200 000 (I08б).
7. **Довга поїздка (понад добу) обмежується одним денним лімітом** і записується лише на день посадки (G08, I06, L13).
8. **Неіснуючі дати й час** (`02-30`, `24:00`) проходять валідацію (L13, L14).
9. **HTTP API не використовує журнал денного ліміту** (M03), тому ліміт «на день» через API фактично діє на кожну поїздку.
10. **Правило округлення T9 недосяжне** з поточними ставками у `quote()` (розділ K). Варто перевірити, чи специфікація не передбачає інших сум (наприклад, відсотків від зборів або іншого порядку знижок), де округлення мало б значення.
