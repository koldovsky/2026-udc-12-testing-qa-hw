# Тест-кейси: розрахунок вартості поїздки (виведено з коду)

Джерело очікувань — **виключно код у `app/src/`** (читання обмежене цією текою за умовою завдання).
Файл `docs/spec/tariffs.md`, на який посилаються коментарі в коді, **не читався**, тому всі очікування
нижче описують **фактичну поведінку реалізації**, а не вимогу специфікації. Розбіжності між кодом і
наміром, які видно з самого коду, винесено в розділ «Підозрілі місця».

Точка входу: `quote(ride, rider, { zones, dayCap })` — `app/src/tariff.js:40`.

## Порядок обчислення (app/src/tariff.js:40–68)

1. `minutes = Math.round((returnAt − pickupAt) / 60000)` (`tariff.js:70`)
2. `timeCharge = minutes < 2 ? 0 : ceil(minutes/30) × RATE` (`tariff.js:74–81`)
3. **Один** тарифний план — абонемент або пільга, **більша знижка** (`cheaperPlan`, `tariff.js:89–98`)
4. Нічна знижка 30 % — на **залишок** після п.3, лише якщо залишок > 0, за **годиною подачі в Києві** (`tariff.js:50–54`)
5. Денний ліміт 30000 коп. — на залишок після п.4 (`tariff.js:56–61`)
6. Збори — **поверх** ліміту; половиняться **лише якщо обраний план = `reduced`** (`tariff.js:63–65`)
7. `total = due + сума зборів` (`tariff.js:66`)

## Базові (дефолтні) вхідні дані

Якщо в кейсі поле не вказано, діє базове значення:

```
ride  = { pickupAt: "2024-06-10T10:00:00+03:00",   // Київ, літо (EEST, UTC+3), 10:00 — не ніч
          returnAt:  "2024-06-10T10:30:00+03:00",
          bike: "classic",
          returnStation: "S01" }                   // зона "in"
rider = { type: "standard" }
opts  = { }                                        // zones = stationZones, dayCap відсутній
```

У колонці «Вхідні дані» вказано **лише відхилення** від базових. Тривалість задається через `returnAt`.

## Підозрілі місця, виявлені при виведенні очікувань

Це не окремі тест-кейси, а пояснення, чому очікування вище саме такі. Чи це дефекти — має показати
звірка з `docs/spec/tariffs.md`, якого я не читала.

1. **TC-31 — немонотонність ціни.** Поїздка пільговика тривалістю 1 хв поза зоною коштує 15000 коп.,
   а тривалістю 30 хв — 8750 коп. Причина: половинення зборів прив'язане до `plan.code === "reduced"`
   (`tariff.js:64`), а при нульовому погодинному нарахуванні знижка `reduced` дорівнює 0 і `cheaperPlan`
   повертає `none` (`tariff.js:90,97`).
2. **TC-19 — половинення зборів залежить від нічиї між планами.** Якщо абонемент і пільга дають однакову
   знижку, обирається `subscription`, і збори не половиняться, хоча право на пільгу в райдера є.
3. **TC-45 — дві різні «доби».** Нічна знижка рахується за київським часом (`kyiv-time.js`), а доба денного
   ліміту — за UTC (`day-cap.js:6–8`). Для поїздок між 00:00 і 03:00 за Києвом влітку (01:00–03:00 узимку)
   доба ліміту «відстає» на день.
4. **TC-37 — ліміт без журналу.** Без переданого `dayCap` ліміт 30000 все одно застосовується, але до
   кожної поїздки окремо, тож за день можна нарахувати більше ніж 30000.
5. **Денний ліміт обліковує лише погодинне нарахування** — збори (TC-39) до нього не входять і до журналу
   не записуються (`tariff.js:61`).
6. **Округлення T9 на практиці не проявляється.** `discount()` округлює залишок донизу (`tariff.js:101–103`),
   але всі можливі суми (кратні 2500/4000, після 20 % і 50 % — усе ще кратні 100) діляться без залишку,
   тому кейсу, де округлення змінює результат, із наявними ставками побудувати не вдалося. Якщо ставки
   зміняться, цей випадок треба буде покрити окремо.
