# Тестові «запахи» в `app/test/unit/`

Обсяг аналізу: `app/test/unit/receipt-format.test.js`, `tariff.test.js`, `server.test.js`, `day-cap.test.js`
(усього 4 файли). Код `app/src/*` і набір `app/test/spec/*` читала як джерело очікуваних значень —
нічого не змінювала.

Контекст, який підсилює всі знахідки нижче: `npm run coverage` (`app/package.json:10`) міряє покриття
**лише по `test/unit/**`**. Тобто саме цей — найслабший — набір є офіційною метрикою якості проєкту,
тоді як сильні таблично-параметризовані тести з `test/spec/*` у метрику не входять.

Позначки важливості: 🔴 критично (тест не перевіряє те, що обіцяє) · 🟠 суттєво · 🟡 дрібно.

## 🔴 1. `tariff.test.js:89` — «a 45-minute classic ride costs 50 UAH»

**Запах:** *Testing the Mock / Mock Overuse* (тест перевіряє власну заглушку).

```js
const priceRide = mock.fn(() => ({ minutes: 45, timeCharge: 5000, ..., total: 5000 }));
const result = priceRide(ride(...), standard);
assert.equal(result.total, 5000);
assert.equal(priceRide.mock.callCount(), 1);
```

**Чому це проблема.** Продакшн-функція `quote` тут не викликається взагалі. Тест оголошує заглушку,
яка повертає константу `5000`, викликає заглушку і перевіряє, що вона повернула `5000`. Це тавтологія:
тест зелений завжди — навіть якщо видалити весь `src/tariff.js`. При цьому назва тесту заявляє перевірку
тарифного правила T3, тож у звіті він виглядає як покриття бізнес-логіки. Другий assert
(`callCount() === 1`) перевіряє, що рядком вище справді стався виклик, — нульова інформативність.
Це найнебезпечніший вид запаху: «брехливий тест», який дає фальшиву впевненість.

## 🔴 2. `tariff.test.js:32` — «e-bikes are billed at the e-bike rate»

**Запах:** *Duplicated Production Logic in Assertion / Self-fulfilling assertion*.

```js
assert.equal(result.timeCharge, Math.ceil(result.minutes / BLOCK_MINUTES) * RATES.ebike);
assert.equal(result.total, result.timeCharge);
```

**Чому це проблема.** Очікуване значення обчислюється тією самою формулою, що і в `src/tariff.js:74-83`

зламається округлення блоків (напр. `Math.floor` замість `Math.ceil`) — тест перерахує по-новому і
залишиться зеленим. Для поїздки 75 хв очікування має бути жорсткою константою `12000`
(3 блоки × 4000), а не виразом. Другий assert порівнює два поля одного й того самого об'єкта, тобто
знову не має зовнішнього оракула.

## 🟠 3. `tariff.test.js:9` — «quote returns an itemised price»

**Запахи:** *Eager Test* + *Assertion Roulette* + *Tautological (vacuous) assertions*.

```js
for (const r of rides) {
  const result = quote(r, standard);
  assert.ok(result.total >= 0);
  assert.ok(Array.isArray(result.discounts));
  assert.equal(typeof result.minutes, "number");
}
```

**Чому це проблема.** Три причини одразу:
1. **Порожні твердження.** `total >= 0` не може бути хибним — ціна ніколи не від'ємна (`src/tariff.js:65`).
   `Array.isArray` і `typeof === "number"` перевіряють форму об'єкта, а не правильність розрахунку.
   Тест пройде, якщо `quote` почне повертати `total: 0` для всіх поїздок.
2. **Eager Test.** В одному тесті — три різні сценарії (1-хвилинна поїздка — межа безплатних 2 хв T2;
   50-хвилинна — два блоки; 130-хвилинна e-bike), і жоден не перевірений по суті. Перший сценарій
   особливо цінний (межа T2), але його очікування `0` не зафіксовано.
3. **Assertion Roulette.** Асерти всередині `for` без третього аргументу-повідомлення: при падінні
   звіт покаже лише «expected true», без вказівки, на якій із трьох поїздок зламалося.

`X01` дає збір 15000, треба відкрити інший файл. Якщо `X01` колись переведуть у зону `in` (звичайна
бізнес-зміна довідника), впадуть тести тарифікації, що з цією зміною не пов'язані. При цьому
`src/zones.js:17` і `quote(..., { zones })` спеціально зроблені для інжекції власної таблиці — unit-тести
цим не користуються (`server.test.js:25` інжектить `page`, але так само не інжектить `zones`).

## 🟡 19. `server.test.js:7-27` — ручний дубль `ServerResponse`

**Запах:** *Over-fitted / fragile test double*.

**Чому це проблема.** Фейковий `res` реалізує лише `writeHead` + `end`, бо саме їх викликає поточний
`send()` (`src/server.js:67-70`). Це прив'язка тесту до внутрішньої деталі реалізації: цілком
валідний рефакторинг на `res.setHeader()` + `res.write()` зламає всі три тести файлу, хоча поведінка
API не зміниться. Крім того `end()` зберігає лише останній чанк, тож потокова відповідь буде
«перевірена» неправильно, без помилки.

## Крос-файлові спостереження

**А. Дублювання з `test/spec/*` у слабшій формі.** `tariff.test.js:65` (нічна знижка) повторює TC-44/TC-58
з `test/spec/t10-night.test.js`, а `tariff.test.js:79` (денний ліміт) — TC-27 з `test/spec/t6-day-cap.test.js`.
У spec-наборі ті самі правила перевірені точними очікуваннями, з повідомленнями в асертах і
посиланнями на тест-кейси. Unit-версії не додають нічого, крім ризику: вони створюють видимість
покриття (а саме unit-набір міряє `npm run coverage`) і при зміні тарифу вимагають подвійного
супроводу. Це класичний *Duplicated Test / Redundant Test*.

**Б. Magic Numbers по всьому набору.** Очікування записані «сирими» числами без розкладки, хоча
`src/tariff.js` експортує `RATES`, `BLOCK_MINUTES`, `OUT_OF_ZONE_FEE`, `NIGHT_PERCENT` тощо:
`tariff.test.js:29` (`5000`), `:44` (`6400`), `:61-62` (`17500`, `15000`), `:68` (`2500`),
`receipt-format.test.js:19` (`5`), `server.test.js:45` (`5000`). Читач не бачить, з чого складається
сума, і при зміні тарифу незрозуміло, які числа перераховувати. Зауважу: тут є компроміс — у
«золотих» значеннях константа іноді **краща** за формулу (див. знахідку №2, де обчислення очікування
вбило тест). Правильний варіант — константа плюс коментар-розкладка, як у `test/spec/*`.

**В. Спільна фікстура між тестами.** `tariff.test.js:7` — об'єкт `const standard = { type: "standard" }`,
спільний для всіх тестів файлу. Зараз його ніхто не мутує, тож дефекту немає, але це *Shared Fixture*:
один тест, який додасть у нього поле (напр. `concession`), непомітно зламає решту. Фабрика
(як `ride()` рядком вище) безпечніша.

**Г. Прогалини покриття в unit-наборі** (важливо, бо саме він у метриці coverage): межа T2
(безплатні ≤ 2 хв, `src/tariff.js:81`) ніде не перевірена точним очікуванням; не перевірено
`rider.concession` та вибір дешевшого з планів `cheaperPlan` (`src/tariff.js:96-105`); не перевірено
`readRider` (невідомий тип користувача, відсутній `rider.id` при `dayCap`); у сервері не покриті
404, 500 і межа `MAX_BODY_BYTES`; у реєстрі — `chargedOn` і розділення діб/користувачів.

**Д. Поза обсягом завдання, але варте уваги.** `app/test/helpers/factory.js` генерує дані через
`Math.random()` без сіду, і його використовує `app/test/integration/receipt.test.js:12-13`. Це
*Non-deterministic / Random Test* — падіння не відтворюється, а частина кейсів перевіряється лише
інколи. У тестах з `test/unit/` ця фабрика не використовується, тож у список знахідок я її не включаю.
