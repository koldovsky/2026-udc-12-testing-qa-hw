## Прогін 1141 — PR #231 «Тести: поїздки в ніч переведення годинника»

**Клас: дефект тесту.**

**Що впало.** Новий тест, який PR додає:

```
✖ a ride on the night the clocks go back is billed by the station clock
  AssertionError: tariff.quote() miscounts the ride across the DST change
  180 !== 120      (actual: 180, expected: 120)
  at …/app/test/unit/clock-change.test.js:11:10
```

Решта 21 тест пройшла (`pass 21 / fail 1`). Diff додає лише цей один файл — змін у `src/` немає.

**Чому.** Тест бере `pickupAt = 2026-10-25T02:30:00+03:00` і `returnAt = 2026-10-25T04:30:00+02:00` і очікує 120 хв, тобто різницю показів настінного годинника (02:30 → 04:30). Але ці два моменти в UTC — `2026-10-24T23:30Z` і `2026-10-25T02:30Z`, а між ними 3 години. Це випливає з самого запису зсувів: +03:00 → +02:00, і година 03:00–04:00 за Києвом повторилась.

`tariff.js` рахує тривалість з абсолютних моментів, а не з годинника на стіні:

```js
const ms = Date.parse(value);                              // instant()
return Math.round((returned - pickup) / 60_000);           // rideMinutes()
```

Тобто 180 — реальний час, який велосипед був у користувача, і код дає його правильно. Вираз у назві тесту «billed by the station clock» і повідомлення «`tariff.quote()` miscounts» — це хибна припущена вимога автора тесту, а не знайдений баг. Другий тест того ж файлу (поїздка напередодні, без зсуву) проходить: `✔ a ride the evening before the change is not affected`. Це підтверджує, що решта тестової обв'язки (фікстура `ride`, виклик `quote`) працює.

**Що виправити.**
1. Вимоги — у тесті `app/test/unit/clock-change.test.js`: `result.minutes` має бути `180`, `result.timeCharge` — `6 * 2500` (блоків `ceil(180/30) = 6`, 15000 коп.). Назву й повідомлення змінити, наприклад «ride across the clock change is billed by elapsed time».
2. Не забути, що пікап о 02:30 за Києвом потрапляє під нічну знижку (`kyivTime(pickup).hour < 6`). За моїм ручним розрахунком `total` = 15000 − 4500 = 10500; якщо тест перевірятиме `total`, то це значення, а не `timeCharge`.
3. Якщо ж вимога продукту справді «за годинником станції» (180 → 120 хв) — це змінює правила тарифу, а не тест; рішення за власником специфікації, і тоді правиться `rideMinutes` в `src/tariff.js` і спека. Я цього не рекомендую: суперечить обліку за абсолютним часом, який уже закладено в коді.

Не перевірено запуском: сам `180` вирахуваний вручну, але збігається з `actual: 180` у логу.

## Прогін 1144 — PR #233 «Сторінка: підказка про збір за поїздку понад добу»

**Клас: нестабільний тест** (недетермінований вхід + хибний очікуваний результат на межах).

**Що впало.**

```
✖ every receipt of a week of rides ends with the amount due
  classic, 60 min from 2026-09-21T08:14:00.000Z:
  got "До сплати .......................... 50,00 грн", expected 75,00 грн
  at …/app/test/integration/receipt.test.js:20:12
```

Перезапуск того самого коміту (`ci/README.md`: «2 — успішно») пройшов. Diff PR змінює лише `public/index.html` (CSS-клас `.hint`, `aria-describedby`, абзац з підказкою) — код тарифу, чека й тестів не зачеплений, а сторінку цей тест не завантажує.

```js
// app/test/integration/receipt.test.js:15
const expected = (Math.floor(minutes / 30) + 1) * PRICE[ride.bike];
```

Тариф рахує `Math.ceil(minutes / 30)` блоків (`tariff.js`, `blocks()`). Формули збігаються всюди, окрім випадку, коли тривалість кратна 30: для 60 хв тест чекає 3 блоки (75,00), а тариф бере 2 (50,00) — рівно те, що в логу. Тариф тут правий: тест `a 45-minute classic ride costs 50 UAH` і 40-хвилинний приклад з README (50,00 грн) узгоджені з `ceil`.

Дані при цьому випадкові: `app/test/helpers/factory.js` бере `between(5, 89)` хвилин через `Math.random()` без seed, 10 поїздок за запуск. З діапазону 5..89 під хибну формулу потрапляють лише 30 і 60 (ще 90 поза діапазоном). За моєю оцінкою це приблизно `1 − (83/85)^10 ≈ 21 %` падінь на кожен запуск — тобто падає приблизно раз на п'ять, і падіння «зникає» після перезапуску. Нічні поїздки в діапазон не входять: старт від 09:00 за Києвом до 19:00 (`DAY_START` + до 600 хв), тому нічна знижка тест не псує. Ймовірність — розрахункова, повторних запусків на `main` я не робив.

Ознака, що це не PR: у лозі 1141, 1147 і 1152 той самий тест `every receipt of a week of rides …` пройшов на інших випадкових даних, а у 1144 він єдиний падає.

**Що виправити.**
1. У `receipt.test.js:15` замінити оракул на `Math.ceil(minutes / 30)` (для `minutes ≥ 2`; поїздки з фабрики ≥ 5 хв), або, ще краще, брати очікувану суму не з копії формули, а фіксованими значеннями.
2. Прибрати недетермінізм: засіяти генератор у `factory.js` (одне seed на запуск, яке друкується в повідомленні при падінні) або перейти на перелік граничних випадків: 29, 30, 31, 59, 60, 61 хв.
3. Окремо від причин: цей PR можна змерджити після повторного зеленого прогону; правка тесту не залежить від нього.

## Прогін 1152 — PR #238 «tariff: спростити feesFor»

**Клас: дефект коду** (регресія в рефакторингу).

**Що впало.**

```
✖ a bike kept over a day and left outside the zone pays both fees
  at …/app/test/unit/tariff.test.js:66:10
  1 !== 2   (actual: 1, expected: 2)
```

Інші 19 тестів пройшли; тест для цього сценарію вже був у `main` і не змінювався.

**Чому.** PR замінює накопичення зборів на ланцюжок ранніх повернень:

```diff
-  const fees = [];
-  if (zone === "out") fees.push({ code: "out-of-zone", amount: OUT_OF_ZONE_FEE });
-  if (minutes > UNRETURNED_AFTER_MINUTES) fees.push({ code: "unreturned", amount: UNRETURNED_FEE });

+  if (minutes > UNRETURNED_AFTER_MINUTES) return [fee("unreturned", UNRETURNED_FEE)];
+  return [];
```

Два незалежні `if` стали взаємовиключними: коли повернення поза зоною (`zone === "out"`), функція виходить на першому `return` і збір за поїздку понад добу (`unreturned`, 2000,00 грн) втрачається. Тест їде 2 доби (`2026-09-16T07:00Z → 2026-09-18T07:00Z`) і повертає на станцію `X03` — тож має бути 2 збори, а повертається 1. Це ще й фінансова помилка: клієнт недоплатить 2000 грн. Про намір функції свідчить і доданий до неї коментар PR: `/** Fees of a ride: T7 out of zone, T8 over 24 h. */` — обидва збори там названі окремо, а не альтернативно.

Те, що тест упіймав регресію, а не сам тест хибний, видно з 1141 і 1144: у цьому прогоні падає старий стабільний тест без жодних змін у ньому.

**Що виправити.** У `app/src/tariff.js` повернути накопичення, зберігши допоміжний `fee()`, якщо він подобається:

```js
function feesFor(minutes, zone) {
  const fees = [];
  if (zone === "out") fees.push(fee("out-of-zone", OUT_OF_ZONE_FEE));
  if (minutes > UNRETURNED_AFTER_MINUTES) fees.push(fee("unreturned", UNRETURNED_FEE));
  return fees;
}
```

Покриття: тест перевіряє лише `fees.length`. Варто додати перевірку кодів і сум (`out-of-zone` 15000, `unreturned` 200000) та випадок «понад добу, але в зоні» (один збір), щоб наступний рефакторинг не пройшов непомітно. Для знижки `reduced` лінія `fees.map(...)` у `quote` не змінюється.

Не перевірено запуском: застосування diff і зелений результат після виправлення.
