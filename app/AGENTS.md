# Правила для тестів велопрокату

## Тести

1. Для продуктових очікувань використовуйте `docs/spec/tariffs.md`: вказуйте ID T1–T10 у назві тесту й рядок специфікації в коментарі або документації. Якщо специфікації немає у видимій теці, прямо позначайте тести з коду як **характеризаційні** й не називайте їх перевіркою правильного тарифу. Підстава: Task A, `docs/test-cases.md` («Що AI вигадав»), та Task B, `docs/bugs/README.md` (0 дефектів знайшли тести з коду).
2. Не створюйте певне числове очікування для неоднозначного правила. Запишіть питання власнику продукту і тестуйте лише однозначну частину; особливо T10 на межах 00:00/06:00 та його поєднання з T4/T5. Підстава: Task A, `docs/test-cases.md` (Q-1–Q-4), і Task C, `ai-runs/c-strengthen.diff` (тест на 06:00 відхилено).
3. Кожен час поїздки записуйте як ISO 8601 з `Z` або offset; для T6 явно вказуйте київську дату взяття та попередні нарахування того самого користувача. Підстава: Task B, `docs/bugs/BUG-5.md` (UTC/Kyiv), та Task A, TC-36/TC-37.
4. Для меж T1/T2/T3/T4/T8 робіть окремий рядок таблиці для значення на межі й по обидва її боки; перевіряйте точні хвилини та копійки. Підстава: Task B, `docs/bugs/BUG-1.md`, `BUG-2.md`, `BUG-3.md`; Task C, `docs/test-quality.md` (слабкі нерівності).
5. Для коштів перевіряйте точні `timeCharge`, знижки, збори, `total` та стан денного журналу. Не обчислюйте очікуване із `RATES`, `BLOCK_MINUTES` або фактичного результату; не замінюйте точне число перевіркою `>= 0` чи `<= DAY_CAP`. Підстава: Task C, `docs/test-quality.md` (запахи #2–#7).
6. Тест має викликати справжній об'єкт перевірки. Не підміняйте `quote` заглушкою, яка повертає очікуваний результат, і не вважайте сам виклик заглушки доказом тарифу. Підстава: Task C, `app/test/unit/tariff.test.js:79-83` та `ai-runs/c-smells.md` (#1).
7. Не видаляйте, не пропускайте й не послаблюйте тест та не міняйте очікувану суму лише для зеленого прогону або вищого mutation score. Перед зміною поясніть її правилом специфікації; зміни в `app/src/` не є способом «посилити тести». Підстава: Task B, `docs/bugs/README.md` (старі тести фіксували дефекти), та Task C, `ai-runs/c-strengthen.diff` (п'ять відхилених AI-перевірок).
8. Для вцілілого мутанта спочатку з'ясуйте, чи змінює він спостережуваний результат на дозволених входах. Якщо так — додайте мінімальний тест з незалежним оракулом і перевірте повторним прогоном; якщо ні — доведіть еквівалентність, а не додайте випадковий assert. Підстава: Task C, `ai-runs/c-after.txt` (M016/M019 та інші вцілілі).
