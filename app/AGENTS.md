# AGENTS.md — `app/`

Правила для агента, який пише або змінює тести в цій теці. Кожне виведене з конкретної
знахідки домашки WS12; звідки саме — таблиця в `docs/test-quality.md`, розділ 5.

## Тести

1. **Очікувані значення — зі специфікації `docs/spec/tariffs.md`, з ID правила (T1–T10) у
   назві тесту; ніколи — з поточної поведінки коду.** Якщо специфікації в теці немає —
   не вигадуй очікування з коду: скажи, що оракула немає, і зупинись.
2. **Не змінюй перевірку чи очікуване значення, щоб тест пройшов, не пояснивши чому.**
   Червоний тест — це питання «хто неправий: код чи тест?». Відповідь шукай у
   специфікації й наводь рядок, на який спираєшся.
3. **Не обчислюй очікуване значення формулою або константою з модуля, який тестуєш.**
   `assert.equal(result.timeCharge, Math.ceil(result.minutes / BLOCK_MINUTES) * RATES.ebike)`
   — не тест, а копія реалізації: зміни ставку, і обидві частини зміняться разом. Пиши
   число літералом, а його розкладку — коментарем (`2 блоки × 40 грн = 8000`).
4. **Кожна перевірка — точне значення (`assert.equal` / `assert.deepEqual`), а не
   нерівність і не `ok`.** `total >= 0`, `total < timeCharge`, `fees.length === 2`,
   `remaining(...) < DAY_CAP` — перевірки, які майже не можуть впасти. `ok` і нерівності
   допустимі лише там, де сама специфікація задає діапазон, а не одне значення.
5. **Перевіряй склад, а не кількість.** Для `discounts` і `fees` звіряй коди й суми
   (`deepEqual`), а не `length`; не звертайся до елементів за індексом (`fees[0]`), бо
   тест має падати від зміни поведінки, а не від зміни порядку.
6. **Тест мусить викликати код, який тестує.** Мок доречний для зовнішньої залежності,
   але не для функції, що є предметом тесту: тест, який перевіряє значення, повернуте
   власним `mock.fn`, лишиться зеленим і після видалення модуля.
7. **Дані тесту — детерміновані.** Без `Math.random()` і без поточного часу
   (`Date.now()`, `new Date()` без аргументу); без `setTimeout`, `sleep` і повторів
   (retry). Один і той самий прогін має давати один і той самий результат.
8. **Моменти часу — ISO 8601 зі зсувом (`2026-09-16T01:10:00+03:00`), а не UTC з
   коментарем «це 01:10 у Києві».** Підбирай дані так, щоб вони могли виявити дефект:
   момент `08:00:00Z` для перевірки київської доби непридатний, бо київська й UTC-дати
   там збігаються.
9. **Кожне граничне значення — окремим рядком таблиці даних, з повідомленням в асерті.**
   Однотипні кейси — цикл по таблиці, а не копії тесту. Межа — це три точки: на ній, на
   крок до неї й на крок після (45 / 46 хв; 1440 / 1441 хв; рівно 2 хв / 2 хв 1 с).
10. **Не прив'язуйся до дослівного тексту повідомлення про помилку, якщо специфікація
    його не задає.** Перевіряй клас помилки й те, що пояснення називає поле, через яке
    запит відхилено.
11. **Якщо специфікація не дає однозначної відповіді — не автоматизуй кейс і не вирішуй
    мовчки.** Винеси питання в розділ «Питання до специфікації» (`docs/test-cases.md`) і
    залиш неоднозначний випадок без тесту.
12. **Не змінюй `app/src/`, `tools/` і `package.json`, щоб підняти метрику тестів.**
    Якщо тест не вдається написати без зміни продакшн-коду — це знахідка, про яку треба
    сказати, а не тихо правити код.

## Команди

| Команда (з кореня репо) | Що робить |
|---|---|
| `npm test` | усі тести застосунку |
| `npm run test:unit` | лише `app/test/unit/` |
| `npm run coverage` | unit-тести з таблицею покриття |
| `node tools/mutate.mjs` | мутаційний бал для `app/src/tariff.js` і `app/src/day-cap.js` |
| `node tools/repeat.mjs 30` | увесь набір 30 разів, падіння по тестах |
