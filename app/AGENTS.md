# AGENTS.md — `app/` (Велопрокат громади)

Правила для AI-агента, який пише або змінює тести в `app/`. Кожне правило виникло з
конкретної знахідки в Task A–C; звідки саме — таблиця в `docs/test-quality.md`, розділ 5.

## Тести

1. **Очікуване значення — лише з документа вимог, ніколи з поточного коду.** Документ
   вимог — `docs/spec/tariffs.md`. У назві тесту — ID правила (`T1`…`T10`, `§4`), у
   коментарі або повідомленні `assert` — рядок специфікації (`tariffs.md:<N>`). Очікування
   записуй числом-літералом у копійках (`assert.equal(r.total, 12000)`), а не формулою.
   Не імпортуй у тест константи з `app/src/` (`RATES`, `BLOCK_MINUTES`, `DAY_CAP`,
   `NIGHT_PERCENT`, …) і не повторюй у тесті обчислення з коду.
   _Перевірка:_ `grep -nE "RATES|BLOCK_MINUTES|DAY_CAP|_PERCENT|_MINUTES" <новий тест>` —
   порожньо; у кожному `test("…")` в `app/test/spec/` є `T<N>` або `§4`.

2. **Якщо специфікації немає** (у теці немає `docs/spec/` чи іншого документа вимог) —
   очікувань з коду не виводь і не видавай за правильні. Тоді:
   - кожен тест, чиє очікуване значення не підтверджене документом вимог, назви з префіксом
     `ASSUMPTION:` і познач коментарем `// ПРИПУЩЕННЯ: <звідки значення — коментар у коді,
     назва функції, загальна норма>; ПИТАННЯ: <що треба підтвердити>`;
   - якщо код суперечить сам собі (коментар чи назва константи каже одне, а гілка робить
     інше), не фіксуй поточну поведінку тестом — запиши це як питання;
   - у фінальній відповіді — окремий розділ «Питання до власника продукту» і число тестів
     з `ASSUMPTION:`.
   _Перевірка:_ `grep -c "ASSUMPTION:" <тести>` дорівнює числу тестів без посилання на
   документ вимог; у відповіді є розділ питань.

3. **Відкриті питання специфікації не перевіряються.** Поведінку з розділу «Питання до
   специфікації» в `docs/test-cases.md` (Q-1…Q-11: межа 06:00, поїздки через 00:00 / 06:00,
   поєднання нічної знижки з абонементом і пільгою, рядки знижок із сумою 0, вичерпність
   переліку §4, …) не
   закріплюй жодним `assert`. Бери вхідні дані, для яких усі тлумачення дають однаковий
   результат (напр. для T10 — взяття о 06:30, а не о 06:00). Мутант, якого можна вбити лише
   рішенням відкритого питання, лишається живим з позначкою «залежить від Q-N». Єдиний виняток —
   Q-11: два тести `ASSUMPTION:` у `test/spec/tariff-s4.test.js` (правило 2) явно називають
   обране тлумачення й питання; їх переглядають після відповіді власника продукту.
   _Перевірка:_ жоден новий тест не використовує вхід, названий у колонці «Варіанти
   тлумачення» питань Q-1…Q-11 (крім тестів `ASSUMPTION:` з `ПИТАННЯ: Q-11`).

4. **Не підганяй тест під код.** Не змінюй очікуване значення чи перевірку, не видаляй тест
   і не додавай `skip` / `todo` / `only`, щоб тест став зеленим. Червоний тест з очікуванням
   зі специфікації — кандидат у дефект коду: зупинись і опиши тест, рядок специфікації,
   очікуване й фактичне. Кожну зміну наявного тесту (зокрема посилення) — перелічи з
   причиною в `docs/test-quality.md` або `docs/bugs/README.md`. Без `retry`, `sleep`,
   `setTimeout` у тестах.
   _Перевірка:_ `git diff -- app/test` не має рядків `-` з `assert` без запису про причину;
   `grep -nE "\.skip|\.todo|\.only|skip:|todo:|setTimeout|retry" app/test` — порожньо.

5. **Межі — з обох боків, кожна межа — окремим рядком таблиці.** Значення на межі і
   на крок за нею: 2:00 / 2:01 хв (T2), 30:00 / 30:01 (T1, T3), 45 / 46 хв (T4), 24 год /
   24 год 1 с (T8), рівно 300 грн / наступний блок (T6), 23:59:59 / 00:00:00 за Києвом
   (T6, T10), год. 05 / год. 06 (T10, без 06:00:00 — Q-2). Значення «десь посередині»
   (40 хв для межі 45) межу не перевіряє.
   _Перевірка:_ для кожної межі з переліку в таблиці тесту є обидва рядки.

6. **Час — київський, і тест має це розрізняти.** Для T6 і T10 хоча б один момент — у `Z`,
   для якого дата чи година за UTC і за Києвом різні (`2026-09-16T21:00:00Z` = 00:00 17.09
   за Києвом), і хоча б один — у зимовому часі (EET, після 25.10.2026). Момент на кшталт
   `08:00Z`, однаковий за датою в UTC і в Києві, київський час не перевіряє.
   _Перевірка:_ у тестах T6 / T10 є момент `…T21:…Z` / `…T22:…Z` і дата після 2026-10-25.

7. **Жодних слабких перевірок.** Заборонено як перевірку результату: `assert.ok(x >= 0)`,
   `assert.ok(a < b)`, `.length`, `typeof`, `Array.isArray`, `arr.some(...)`,
   `includes` / `endsWith` для сум. Сума — `assert.equal(r.total, <число>)`; знижки й
   збори — `assert.deepEqual(r.discounts, [...])` / `assert.deepEqual(r.fees, [...])`, коли
   склад рядків однозначний за специфікацією (інакше — правило 3); рядок чека — повністю.
   _Перевірка:_ `grep -nE "assert\.ok\(|\.length,|\.some\(|endsWith|includes\(" <новий тест>`
   — порожньо або кожен випадок пояснено коментарем.

8. **Не мокай те, що тестуєш.** Тест викликає справжні `quote`, `createDayCap`, `formatUah`,
   `createHandler`; `mock.fn` — лише замість залежності (годинник, мережа), ніколи замість
   функції, яку перевіряє тест.
   _Перевірка:_ у тесті, який називає поведінку `quote`, є виклик `quote(`.

9. **Один кейс — один рядок таблиці з ID у повідомленні; одна поведінка — один тест.**
   Однотипні кейси — таблицею (`for (const { id, … } of [...])`) з `assert.equal(…, id)`;
   різні поведінки (два ендпоінти, три формати) — різні тести, без «and» у назві.
   _Перевірка:_ кожен `assert` у циклі має третій аргумент з ID кейсу.

10. **Мутант, що вижив, — тест зі специфікації, доказ еквівалентності або «залежить від
    Q-N».** Не пиши тест «щоб убити мутанта» з очікуванням, узятим з коду. Еквівалентність —
    лише з доказом (множина досяжних значень, для яких зміна нічого не міняє); «надто
    складно» чи «нереалістично» — не аргумент.
    _Перевірка:_ кожен мутант у `docs/test-quality.md`, розділ 4, має одну з трьох позначок.
